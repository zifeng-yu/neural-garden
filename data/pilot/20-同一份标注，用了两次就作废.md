# Day 2｜同一份标注，用了两次就作废

> 日期：2026-09-09
> 预计阅读：22 分钟
> 今日只回答一个问题：qrels 在训练和评估中分别扮演什么角色，为什么同一批数据既拿来调参又拿来汇报，会让整组指标失去意义？

## 开场：事情从哪里开始失控

假设场景。你花了一整个下午给 Neural Garden 写评估集：40 条真实查询，每条都标注了应该命中的 chunk，存成 JSONL。然后跑了一遍向量检索，Recall@10 是 0.52。你看着那些失败案例，发现 chunk size 太大导致边界切断，于是把 chunk size 从 800 调到 400，重跑——0.61。继续看失败案例，发现 Top-K 设得太小，从 10 调到 20——0.73。你很满意，在笔记里写下"向量检索 Recall@10 从 0.52 提升到 0.73"。

两周后，你在面试中说："我的检索系统 Recall@10 达到 0.73。"面试官问："这个数字怎么得到的？"你说："在我的评估集上测的。"面试官追问："调参过程中你看过这些查询的结果吗？"你说是。面试官停了一下，说："那这个 0.73 不代表你的系统真正的检索能力，它只代表你的系统对这 40 条查询的过拟合程度。"

你没做错任何一步计算。你错的是把同一份数据用了两次——一次当老师（指导你调参），一次当考官（验证你的水平）。

## 先给结论

qrels 不是一种固定角色的东西，它的角色取决于你拿它做什么。当你用它来观察失败模式、调整参数、选择 chunk 策略时，它是训练信号（training signal）——你的系统正在"学习"这批特定查询的特征。当你用它来汇报最终指标、声称系统达到了某种水平时，它是考试答案——用来测量系统对未见情况的泛化能力。

同一批数据不能同时承担这两个角色。原因不是道德洁癖，而是信息论：一旦你根据某组查询的反馈调整了系统，系统的参数就已经"编码"了这批查询的特征。再用同一批查询测量，测到的不是系统处理新问题的能力，而是系统记忆旧问题的能力。这和 ML 中用训练集报告测试准确率是完全相同的错误——data leakage（数据泄漏，指训练阶段的信息不当地流入了评估阶段，使评估指标虚高）。

对 40 条查询的个人知识库来说，这并不意味着你需要 4000 条标注。你需要的是纪律：把有限的标注切成互不重叠的用途，然后诚实地报告每一部分有多大、能证明什么、不能证明什么。

## 事情为什么会这样

把因果链走完整，用一个尽量小的例子。

### qrels 到底是什么

qrels（query relevance judgments，查询相关性判定）是一份清单，每一行记录三件事：一条查询、一个文档（或 chunk）的标识、一个相关性判定。最简形式是二值的——这个 chunk 和这条查询"相关"或"不相关"。更精细的版本会有分级（0/1/2/3，分别代表不相关、部分相关、相关、高度相关）。在 TREC（Text REtrieval Conference，信息检索领域最权威的国际评测）的标准格式里，qrels 文件长这样：

```
query_id  iteration  doc_id  relevance
q001      0          chunk_037   1
q001      0          chunk_142   2
q001      0          chunk_891   0
q002      0          chunk_055   1
...
```

`iteration` 字段是 TREC 历史遗留，一般填 0，不影响你理解核心概念。关键事实是：一行 qrels 不代表"这个文档存在"，它代表"人类判定这个文档和这条查询的关系"。

### 同一批 qrels 被用两次时会发生什么

你有 40 条查询和对应 qrels。第一次跑系统，Recall@10 = 0.52。你打开失败案例列表，逐条看：

- q007 没召回 chunk_203，因为 chunk_203 被切到了上一个 chunk 的末尾 → 你把 chunk size 改小。
- q019 没召回 chunk_411，因为 Top-10 截断时它排第 13 → 你把 Top-K 改到 20。
- q031 没召回 chunk_678，因为 embedding 对"试用期"和"实习期"编码太近 → 你换了一个 embedding 模型。

每次改动都有道理。每次改动之后你都重跑 40 条查询看效果。问题是：你每一次"看效果"，都在让系统的参数向这 40 条查询的特征靠拢。改 chunk size 是在适应这批查询的措辞长度分布；改 Top-K 是在适应这批查询的相关文档在向量空间中的排名分布；换 embedding 是在适应这批查询的语义模式。

等你改完所有参数，0.73 这个数字反映的是：一个专门为这 40 条查询优化过的系统，在这 40 条查询上的表现。它不能告诉你系统面对第 41 条查询时会怎样。

这和你在 ML/DL 项目 Day 5 学到的结构完全对称：

| ML/DL 语境 | 检索语境 | 泄漏方式 |
|---|---|---|
| 训练集 | 你反复查看并据以调参的查询集 | 模型参数编码了训练样本的特征 |
| 验证集 | 你用来选择超参数的查询集 | 超参数选择偏向验证集分布 |
| 测试集 | 你只在最终汇报时使用一次的查询集 | 如果测试集被提前看过，就不再独立 |
| data leakage | 调参用的查询集 = 汇报用的查询集 | 指标虚高，无法泛化 |

### 那应该怎么做

标准做法是把标注数据切成三份，职责严格不重叠：

**训练集（train）**：用来让模型学习参数。在检索语境里，如果你有可训练的组件（比如 Learning to Rank 模型、fine-tune embedding），训练集是它们更新权重的依据。对 Neural Garden 当前阶段，可能没有需要训练的参数——这种情况下训练集可以为空，这不是问题。

**验证集（validation / dev）**：用来选择超参数和做设计决策。chunk size 用多少？Top-K 设多少？用不用 Hybrid？这些决策应该在验证集上做，因为你允许自己反复看结果、反复调整。验证集上的指标可以指导方向，但不能作为最终汇报数字。

**测试集（test）**：用来做一次性的最终评估。系统设计完成后，在测试集上跑一次，记录指标，此后不再根据测试结果修改系统。如果你又改了，测试集就退化成验证集，你需要一份新的测试集。

对个人知识库的 40 条标注，一个合理的切法是：20 条验证集、20 条测试集、训练集暂时为空。20 条测试集不够大，统计置信区间很宽——这没关系，后面会讲怎么诚实地处理它。关键是：两个集合的角色不同，你不能用验证集上挑出来的结果去汇报系统水平，也不能在看了测试集结果之后再改系统。

### 小数据集的诚实表达

40 条标注、20 条测试集，Recall@10 = 0.73 到底意味着什么？

二项分布下，20 次试验中观察到 73% 成功率，95% 置信区间大约是 [49%, 90%]。这个区间非常宽，意味着真实 Recall 可能低到一半，也可能高到九成。所以如果你在面试中说"我的系统 Recall@10 是 0.73"，这个数字的信息量远不如你说"在 20 条独立测试查询上，Recall@10 的观测值是 0.73，95% 置信区间约 [0.49, 0.90]，测试集偏小，置信度有限，但足以检测大幅度退化"。

后者听起来不够利落，但它不会让你在追问下陷入困境。小数据集不是缺陷，把小数据集伪装成大结论才是缺陷。

## 放回三个项目中看

### ML/DL 概念层

Day 5 你学过 data leakage 的经典案例：用全量数据做特征标准化，再划分 train/test，test 集的分布信息已经通过均值和方差泄漏给了训练过程。今天的检索场景是同一个错误的另一种面孔：用全量查询做调参，再汇报指标，查询的分布信息已经通过你的人工判断泄漏给了系统参数。核心纪律相同——信息的流向必须单向：训练 → 验证 → 测试，不能反向流动。

后续你会学到 Bi-Encoder 和 Cross-Encoder。如果将来你要 fine-tune 一个 embedding 模型，train/validation/test 的划分会直接决定模型是否可信。今天的检索评估是那次训练的预演——区别只是现在你评估的是一个固定的 pipeline，将来你评估的是一个可学习的模型。纪律从现在就要建立。

### Neural Garden 项目层

根据任务建立时提供的项目状态快照：系统没有可量化的 Retrieval Evaluation baseline。这意味着连 Day 1 说的那个最基础的"冻结查询集 + qrels + 指标脚本"都还不存在。所以今天的结论对 Neural Garden 有非常具体的行动指引：

第一步不是"建立完美的评估体系"，而是手写 40 条查询、标注 qrels、切分成 20+20、写一个跑指标的脚本、记录当前向量检索的 baseline 数字。这件事一个下午可以做完。做完之后，你就有了验证集来指导后续调参，有了测试集来汇报数字（附带置信区间和样本量声明），有了回归检测能力——每次改动重跑验证集，如果 Recall 下降超过阈值就报警。

快照里提到的 Search Session 和 Feedback Event 是天然的查询来源：真实用户搜索记录比你自己编的查询更有价值，因为它们的措辞、缩写、错误拼写都是你没有预料到的。但使用时仍要遵守划分纪律——这些查询进入评估集后，就不能再被用来指导针对它们自身的优化。

## 最容易踩的两个坑

**坑一：把"看了测试结果再改系统"当作正常迭代。** 这是最隐蔽的泄漏，因为每一步都看似合理——"我就看了一眼哪里错了，改了一个小参数"。但只要你看了一次测试集结果并据此修改了任何东西（哪怕是一个阈值），测试集就从"独立考官"变成了"参与训练的老师"。正确的做法是：测试集跑完、记录、锁文件。如果确实发现了需要修复的问题，把那条查询移到验证集，在验证集上完成修复，然后用一个新的、从未见过的测试查询替换它。

**坑二：忽略标注者偏差（annotator bias）。** 你给自己的系统标注 qrels 时，几乎必然偏向自己的理解方式。你知道"试用期请假"应该命中哪个 chunk，因为你写过那个 chunk。但另一个用户搜"新员工入职后能不能请假"时，他心里想的相关 chunk 可能和你标注的不同。对个人项目来说，这不是致命问题（用户就是你自己），但在面试中你应该主动提到这个局限："当前 qrels 由单人标注，未做标注一致性校验（inter-annotator agreement），所以指标反映的是单人视角下的检索质量。"——这句话比任何漂亮的数字都更能展示你理解评估的本质。

## 面试官可能继续追问

**"如果测试集只有 20 条，你怎么判断一次改动是真实改进还是统计噪声？"**

回答骨架：

1. 先给结论：20 条测试集上，单次 Recall 变化的置信区间很宽，所以我不会只看总分差异就宣布改进，而是看逐查询 diff 和分组指标。
2. 再解释原因：如果改动让 15 条查询不变、3 条变好、2 条变差，总分涨了两个百分点——这大概率是噪声。如果改动让困难组（关键词精确匹配类）从 0.2 涨到 0.6，其他组不变——这个方向性变化即使样本小也值得重视，因为它指向了一个具体的失败模式被修复。
3. 落到项目："Neural Garden 当前阶段，评估集的首要价值不是产生一个可对外宣称的数字，而是让每一次 pipeline 变更有可追踪的证据链。20 条测试集足以拦截大幅退化，不足以精确比较两个相近的系统——我知道这个边界，不会越界解读。"

## 合上文档前的 60 秒

今天最重要的三句话：

- qrels 的角色取决于你用它做什么：指导调参时它是训练信号，汇报指标时它是考试答案，同一份数据不能同时承担两种角色。
- 数据泄漏不需要"作弊意图"——看了一眼测试结果再改参数，泄漏就已经发生。
- 小数据集不是问题，把小数据集的指标包装成大结论才是问题。
