# Day 14｜当面试官问"这项目真的做完了吗"

> 日期：2026-09-21
> 预计阅读：约 28 分钟（综合收束篇）
> 今日只回答一个问题：Neural Garden 还没有检索评估基线，怎样把它讲成一个可信的求职项目？

## 开场：事情从哪里开始失控

假设场景：面试进行到第二十五分钟。你打开 Neural Garden 的架构图，讲了 Markdown 分块、概念抽取、向量检索、知识图谱，听起来像一个功能齐全的 RAG 产品。面试官点点头，问了一个问题："你这个系统，检索的 Recall@10 是多少？和 BM25 对比过吗？"你心里清楚混合检索根本没进默认链路，但话到嘴边变成了："还没正式测，但效果应该不错，毕竟用了知识图谱。"面试官在简历上画了个圈，换了话题。那一刻，前面二十分钟建立的所有印象开始塌方——不是因为你做少了，而是因为你把没验证的话说满了。

## 先给结论

面试官无法当场运行你的代码，他们唯一能检验的是你的叙述方式。可信度不来自功能清单的长度，而来自三件事：边界清晰（哪些做了、哪些没做、一句话说得准）；结论有证据（数字、测试、结构，能经得起往下追问两层）；取舍有理由（为什么先做这个、后做那个、什么证据会让你改变主意）。

Neural Garden 当前的真实状态——默认检索链路只有向量召回、没有评估基线——在"功能清单"式叙事里是劣势，但在"工程判断"式叙事里恰恰是最值钱的素材：它说明你知道"功能多不等于有效"，并且已经把补救路线排好了顺序。绝大多数候选人只会讲自己堆了什么，不会讲自己为什么停在这里。能把"没做完"讲成一条有依据的路线，本身就和"会写代码"一样稀缺。

但这条路线成立的前提，是过去十三天建立的分层心智模型是真的：每个阶段的输入、输出、失败位置、评估位置，你指得出来。指不出来，"我知道我缺 baseline"就只是一句背好的台词，第二个追问照样穿帮。所以今天的任务不是学新东西，而是把整条链条画一遍，把你准备说的每一句话钉在证据或者明确的"未验证"标签上。

## 事情为什么会这样

一个没有证据的技术结论，是这样在追问链里崩塌的。

假设你说："我的知识库用了 GraphRAG，图谱让检索更聪明。"这句话会打开一棵追问树：图检索在默认召回链路里吗？（按任务建立时的快照：不在，只有 Knowledge Unit 向量召回。）多跳查询的实际例子跑通过吗？图和向量的结果冲突时以谁为准？打算怎么证明图的收益不是随机波动，做过消融吗？边是 LLM 抽取的，错误率量过吗？四个问题全部没有测量结果可以接。此时面试官对你的判断从"项目有短板"升级为"候选人分不清自己做过什么和想象过什么"——项目降级为教程复现，叙述整体打对折。

同样的系统，换一种说法试试："我的检索目前只有向量召回一条路，评估数据集还没建，基线数字不存在，所以我不敢说它好到什么程度。我能给出的可核查事实是：本地 54 项测试守着解析与存储的正确性，10 张 SQLite 表存结构化数据和关系证据，每条概念关系都能回溯到 document 和 chunk。下一步我计划先建版本化 qrels 和向量基线，再用同一把尺子对比 BM25、混合与纯向量的差别，用数据决定要不要上 Reranker。"

两种说法的事实内核完全一样——图没进链路、评估没做。差别只在第二种说法把每个声明打了状态标签，而面试官可以对每个标签继续追问，且每个追问都有答案。追问接得住，可信度就开始累积；接不住，前面说得越漂亮塌得越快。这就是为什么"精确地知道自己没做什么"是面试里最强的信号之一：AI Backend 岗位日常生产的就是"在不确定中做可验证的决策"，把计划说成实现，等于在这个岗位最核心的维度上主动交白卷。

给每个结论打状态标签，可以用一个 14 天里老朋友式的结构来强迫自己诚实（数字均为示意，不是 Neural Garden 的真实测量）：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Claim:
    """每个想说出口的技术结论，先填进这个结构"""
    statement: str   # 例："RRF 混合检索优于纯向量召回"
    status: str      # "measured" | "planned" | "assumed"
    evidence: str    # measured 时：数据集版本 + 指标 + 数字
    next_step: str   # planned 时：拿到证据需要做什么

Claim(
    statement="RRF 优于纯向量",
    status="planned",                      # ← 诚实的标签
    evidence="尚无：需先建 qrels 与 vector baseline",
    next_step="Evaluation Runner + 三组对照实验",
)
```

规则只有一条：`status` 不是 `measured` 的结论，说出口时不能携带任何效果形容词。

## 把系统画出来

一条完整链路，标上任务建立时快照的真实状态：

```
 已实现(快照)                未进默认链路                  评估/反馈层
──────────────────────      ──────────────────────        ─────────────────────
文档 → 分块(Header/递归)      BM25 ──┐
  → LLM 提取 KU/Concept             ├→ RRF → Rerank/LTR
  → Embedding → Chroma 向量召回 ────┘        ↓
  → Concept 归一(召回+LLM判等)      有序上下文 → Answer
  → 关系 + Evidence → SQLite            ↓        ↓
  → NetworkX 运行时构图            Citation   No-answer
  → Session/Feedback 记录      ⛔ 以上均未实现，按需逐层验证
  ⚠ 双写无共享事务(missing/        ↑
     stale vector 风险)    ┌───────┴────────────────────┐
                           │ 版本化 qrels + Eval Runner │ ← 一切效果
                           │ + Vector baseline          │   声明的地基
                           └────────────────────────────┘
```

看这张图的姿势不是扫功能，而是逐列自问：这一列输入是什么、变换是什么、输出给谁、在哪失败、用什么指标测。第 1–2 天给了证据标准，第 3 天给了候选集天花板，第 4–6 天给了排序三兄弟的边界，第 7 天走通了半程，第 8–10 天给了 contract、异常与双写一致性，第 11–12 天给了图的正确用法，第 13 天给了生成侧评估。合上图，链条就回到你手里。

## 放回三个项目中看

### ML/DL 概念层

Day 1–6 已经给了你最底层的"证据语言"：混淆矩阵、Recall@K、MRR、nDCG、train/validation/test、数据泄漏——这些概念在本文里全部换了马甲出现：qrels 是标注语言，baseline 是控制变量，消融是 validation 的检索版。XGBoost 与 Learning to Rank 的答卷（ML 项目 Day 7）仍未提交，后面的 Tensor、Attention、Bi-Encoder/Cross-Encoder 也还没系统学完。面试里被问到 embedding 内部机制时，诚实的说法是"目前把 embedding 当可靠黑盒使用，训练机制在系统学习中，但我清楚它在链路里承担什么、在哪失效"——这句话每个成分都有依据。

### Python / AI Backend 工程层

第 8–10 天提供的是讲项目的"骨架语言"：Retriever contract 让组件可替换、可 mock、可测试；connect/read 超时与可重试/终态错误的划分，决定 embedding 批量入库任务的健壮性；双写 reconciliation（SQLite 事务与 Chroma 外部写入没有共享事务，靠版本戳、ingestion status 和对账流程兜底）是整个项目最有后端味道的故事。"54 项测试通过"守护的是解析与存储的正确性，不是检索的相关性——分得清这两种证据，本身就是工程成熟度。

### Neural Garden 项目层

依据任务建立时提供的项目状态快照：已实现的是分块、KU/Concept 提取、概念归一、关系与证据回溯、SQLite/ChromaDB/NetworkX 三存储、Insight、会话与反馈记录、Knowledge Unit 向量检索；未实现的是 BM25、Hybrid、RRF、Reranker、LTR、图检索进链路、Answer、Citation、No-answer、HTTP API、Agent。今天的知识直接决定三个判断：为什么 top-ROI 路线把评估排第一（没有基线时任何改动的效果不可归因）；为什么内容 hash 必须覆盖 prompt、模型与配置版本（证据的可追溯性依赖实验条件可复现）；为什么删除重建式的文档更新要先解决——否则评估集测到的是一个会随机损坏的系统。而决定 BM25、Reranker、图检索"要不要做"的证据是同一种东西：版本化 qrels 上相对向量基线的指标增量，加至少一组消融。

## 最容易踩的两个坑

**坑一：状态词失控，把"计划"说成"已经"。** 一词之差："我实现了混合检索"对比"我设计了混合检索的验证方案，尚未实现"。前者在第二个追问就崩塌，而崩塌会被面试官归因到诚信而非能力——技术缺陷可以培养，叙述失真一票否决，且一处失真会让整份简历被重新打折。防御方式就是上面的 Claim 结构：开口前，每个结论先打标签。

**坑二：把"没有数字"讲成"没有标准"。** 因为没测过指标，就退回"效果挺好""比较智能"这种主观词；或者更糟，把行业里流传的经验数字安到自己项目上。没有指标数字时，正确的替代品是可核查的过程证据（54 项测试、10 张表、证据可回溯到 chunk）加一份具体到步骤的评估计划。"我不知道它现在有多好，但我知道怎么在两周内让它变得可测"——这句话不是退让，是资深信号。

## 面试官可能继续追问

**追问：**"你说先补评估。那这个评估数据集从哪来——查询谁写的、标注谁做的、一百多条够吗、有什么泄漏风险？"

回答骨架：
1. **先给结论**：查询从真实使用场景来（Neural Garden 已有 Search Session 记录，可直接转化为查询样本，辅以自己手写的目标查询），qrels 版本化冻结后不再改动。
2. **再解释原因**：查询分布决定指标的意义——用"自己写的、知道答案在哪篇文档的查询"测检索，天然偏乐观，要有意混入模糊表述和跨概念查询；调参只能用 validation 子集，冻结的 test 子集只在方案定稿时跑一次，否则就是第 2 天讲过的评估泄漏。
3. **落到项目**：小数据集的诚实表达是报告绝对数与逐查询位次（120 条中命中多少条、错在哪条），而不是一个精确到小数点后三位的平均分。HTTP API 上线后，线上真实查询会替换手写样本，评估集跟着版本演进。

## 合上文档前的 60 秒

今天最重要的三句话：
1. 面试可信度 = 边界清晰 × 结论有证据 × 取舍有理由，功能数量只是分子里最小的一项。
2. "没做完但有明确验证路线"是 AI Engineer 岗位的真实工作语言；把弱点讲成路线的前提，是你知道每一层怎么失败、怎么测量。
3. 每个说出口的技术结论，要么跟一个数字，要么跟一个"计划"标签——不跟形容词。

60 秒问题：现在在脑子里对 Neural Garden 做一次 3 分钟默讲。你刚才用到的每一个效果性表述，证据是什么？说不出证据的那一句，就是要改写的那一句。

### 1. 这 14 天串起来的完整能力链

### 4. 一份 8–10 分钟的 Neural Garden 面试介绍骨架

只给时间分配和锚点，不要写成背诵稿：

- **0–1 分钟｜问题与动机**：个人 Markdown 知识库的痛点不是存不下，而是搜不准、连不起来、说不清依据。目标：检索 + 概念关系 + 证据回溯。
- **1–3 分钟｜架构走查**（用今天的整图）：Header 分块与递归字符分块 → LLM 提取 KU/Concept → Embedding 入 Chroma → 向量召回 → Concept 归一（向量召回候选 + LLM 判等）→ 关系与 Evidence 落 SQLite → NetworkX 运行时构图 → 会话与反馈记录。强调一句：SQLite 是结构化事实来源，图不持久化。
- **3–5 分钟｜我做的关键判断**（挑三个讲透）：① 概念归一不用纯相似度阈值，用召回 + LLM 判等，因为同义异名和同名异义会同时骗过阈值；② 图从 SQLite 重建而非独立持久化，避免第三份状态引入一致性负担；③ 关系必须带 Evidence 指针，因为边来自 LLM 抽取，可回溯是唯一的纠错通路。
- **5–7 分钟｜坦白的工程短板**（每个都带原因）：无 retrieval baseline；BM25/RRF/Reranker/图检索/Answer/Citation 均未进默认链路；SQLite 与 Chroma 双写无共享事务，存在 missing/stale vector 风险；更新采用删除重建，失败会丢上一可用版本；内容 hash 尚未覆盖 prompt/模型/配置版本。
- **7–9 分钟｜路线与理由**：为什么 evaluation 排第一；hybrid → rerank → ingestion 可靠性 → reconciliation → 图消融的顺序逻辑；每个"做不做"都由指标增量与消融决定，而不是由文章决定。
- **9–10 分钟｜收束与反问**：这个项目最大的收获是把"结果不好"拆成了可定位、可测量的分层问题。留一个开放问题给面试官（例如"如果是你评审，图消融和 HTTP API 哪个先做？"），把对话从审讯变成评审。

### 5. 面试官最可能继续追问的五个问题

1. 你的向量召回 Recall@10 现在是多少？还没测的话，两周后你打算怎么测？
2. SQLite 提交成功、Chroma 写入失败，用户此刻搜索这篇文档会发生什么？你怎么发现、怎么修？
3. Concept 归一那步 LLM 判等错了（把两个不同概念合并），图、证据、检索各受什么影响？有回滚手段吗？
4. 为什么不直接用 LangChain/LlamaIndex 搭一套？哪些部分你坚持自己写，为什么？
5. 加了 GraphRAG 之后，你打算设计什么对照实验，证明多跳收益不是随机波动？

每题只准备三件事：直接结论、机制解释、项目落点——不写逐字稿。
