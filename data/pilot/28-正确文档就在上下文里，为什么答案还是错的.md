# Day 13｜正确文档就在上下文里，为什么答案还是错的

> 日期：2026-09-20
> 预计阅读：20–24 分钟
> 今日只回答一个问题：答案生成、引用展示、拒答这三种行为，各自需要什么样的证据？

## 开场：事情从哪里开始失控

（假设场景）一个团队做完知识库问答系统的阶段性评审。检索评估结果很好看：换上 Hybrid + RRF 之后，Recall@5 从 0.72 涨到 0.85。会上老板问："那答案的正确率呢？"工程师想了想，现场跑了个 demo——问了十个问题，答得头头是道，还都带着来源链接。众人点头，评审通过。

三周后用户投诉：一个配置项问题，系统给出了明确参数值，并引用了第 12 号 chunk。但翻开第 12 号 chunk，里面根本没有这个参数；答案数字来自模型自己"记忆"里的旧版本默认值。检索没做错——正确的文档确实进了 Top-5；做错的是后面那段没人评估过的路。

今天追究的就是这一段：**从"正确文档进了上下文"到"用户拿到可信答案"之间，还有三个独立的行为，每个都需要自己的证据。**

## 先给结论

检索指标和答案指标测量的是两个不同的失效面。Recall@K、nDCG 回答的是"对的文档有没有进入上下文"；答案评估回答的是另一串问题："给了上下文，它说对了吗？说的是上下文里有依据的话吗？没依据的时候它停下了吗？"前者提高不蕴含后者提高，因为生成阶段会引入检索层指标根本看不到的新失效模式：无视上下文凭参数记忆作答、关键内容在长上下文中段被"读丢"、多篇文档整合失败、证据不足时不肯拒答。

所以答案层评估至少要拆成三类信号：**答案正确性**（Answer Correctness，需要 gold answer 或可靠 judge）、**引用忠实度**（Faithfulness / Citation Quality，需要"陈述 → 被引段落"的可验证蕴含检查）、**拒答行为**（Abstention / No-answer，需要一份明确标注"不可回答"的题集）。三者对应三类不同的失败，谁也替代不了谁。

这也解释了一个反直觉现象：为什么认真做端到端评估的团队， sometimes 会在检索指标大涨的同一周，把生成链路整个回滚——因为他们第一次发现，系统以前有近三分之一的回答根本没有证据支撑，只是没人量过。

## 事情为什么会这样

把今天的主因果链摆出来：

```
检索对 → 文档进上下文 → 模型使用上下文 → 输出陈述 → 引用支撑 → 用户可信
              ↑ 每一环都可能独立断掉，
              断在哪环，就必须用那一环的指标才能看见
```

### 一个迷你数据集

假想 100 个评测问题：70 个可回答，30 个是专门构造的"库里没有答案"的题。检索层 Recall@5 = 0.85。现在跑端到端，把结果摊开：

| 情形 | 数量 |
|------|------|
| 可回答，答对 | 48 |
| 可回答，答错 | 19 |
| 可回答，但拒答了 | 3 |
| 不可回答，却自信作答（幻觉） | 25 |
| 不可回答，正确拒答 | 5 |

只看"答对 48%"你会觉得还行；但看那 25 道不可回答的题——系统把三分之二的瞎编当成答案交付了，还带着看起来很专业的引用链接。**这就是只有检索指标时你永远看不见的失败面。**

### 为什么文档在场，答案还会错

三类机制，按发现顺序讲：

1. **位置效应。** 论文《Lost in the Middle》（Liu et al., 2023，已在线核对摘要）系统测量了一个现象：当关键信息位于长上下文的开头或结尾时，模型表现最好；位于中间时显著变差，呈 U 形曲线——即使是宣称支持长上下文的模型也不例外。映射回我们的系统：你检索把正确文档放进了 Top-5，不等于它被"看进眼里"。拼上下文时的顺序，本身就是质量变量。
2. **参数记忆与上下文打架。** 模型"记得"的旧默认值和文档里的新值冲突时，它可能选择相信自己的记忆。这就是为什么"有引用格式"不等于"忠实于证据"。
3. **多文档整合。** nDCG 告诉你每篇文档单独相关，但一道题要综合三个 chunk 里的人物、时间和数字才能回答时，整合难度不体现在任何单篇分数里。ALCE 论文（Gao et al., EMNLP 2023，已在线核对）的结论之一正是：跨多来源综合是当时系统的最大短板，最强模型在 ELI5 上也有超过一半的陈述缺乏完整引用支撑。

### 引用要证明的是蕴含，不是共现

一个可信引用长这样：答案拆成一条条独立陈述（claim），每条陈述与被引 chunk 做 entailment（蕴含）判断——"chunk 12 是否真的支撑'默认值是 8'这句话？"可用 NLI 模型或 LLM judge 执行。RAGAS 框架（Es et al., 2023）把这类"上下文利用是否忠实"作为独立评估维度，正对应上面的 claim 检查。链接、角标、"根据[3]"这些话术，只是引用的**外观**；蕴含关系才是引用的**证据**。

### 拒答评估，其实就是你第一天学的那个东西

30 道不可回答题 + 70 道可回答题，系统每题选择"作答/拒答"——这是一张标准混淆矩阵。"不可回答却作答"是幻觉，"可回答却拒答"是过度拒答（over-refusal），两个方向的错要分开报数。一个 60 行的评分器骨架：

```python
from collections import Counter

def score_answers(cases):
    # case: .answerable, .abstained, .correct(bool|None)
    s = Counter()
    for c in cases:
        if not c.answerable:
            s["hallucinated" if not c.abstained else "correct_refusal"] += 1
        else:
            if c.abstained:
                s["over_refused"] += 1
            elif c.correct is None:
                s["judge_failed"] += 1   # judge 挂了 ≠ 答错了
            else:
                s["correct" if c.correct else "wrong"] += 1
    return s
```

注意 `judge_failed` 那一格：LLM judge 本身是外部依赖，它超时、限流、返回无法解析的 JSON 时，你必须把"没判成"和"判为错"分开。这和你之前"测试看似命中、实际提前返回绕过目标路径"是同一类错误——评估代码悄悄短路，比没有评估更危险。

### 今日主动记忆术语（5 个）

Context Relevance（上下文相关性）、Answer Correctness（答案正确性）、Faithfulness（陈述与证据的忠实性）、Citation Quality（引用质量）、Abstention / No-answer（证据不足时拒答）。

## 把系统画出来

```
        ┌── 检索评估（Day 1-2 已讲）──┐   ┌──── 端到端答案评估（今天）────┐
query → Retriever → Top-5 context → Generator → answer + citations → 用户
        │                              │
        │ 失败A: 正确文档没进候选        │ 失败B: 进了上下文但被忽略/位置差/整合错
        │ （Day 3: 排序器的天花板）      │ 失败C: 编造无证据支撑的陈述
        │                              │ 失败D: 证据不足仍作答（该停不停）
        ▼                              ▼
   qrels + Recall@K/nDCG        gold answers + 不可回答题集
                               + claim 级引用校验 + 2×2 拒答表
```

一句话读法：**A 类失败用 qrels 量，B/C/D 类失败各配一套独立证据；缺哪套，哪类失败就永远隐身。**

## 放回三个项目中看

### ML/DL 概念层

- Day 1 的混淆矩阵今天原样复活：拒答评估就是 answerable × abstained 的 2×2，"幻觉"是最贵的那格 FP。
- Day 2 的数据划分继续有效：gold answer、judge 的 prompt、拒答阈值，全部属于"调参资源"，若在同一份评估集上反复调，答案指标同样会虚高。
- Day 3 的候选天花板思想被延伸：检索决定上限，但**达到上限不保证产出正确**——两层是串联的独立失效面。
- 为后续 Transformer 部分埋的点：位置效应本质是 attention 在长输入上的分布问题，学到 Mask 与位置编码时你会回头看今天。

### Python / AI Backend 工程层

生成器的返回值 contract 不该是裸 `str`。用 Day 8 的方式写：`answer: str | None`、`citations: list[Citation]`、`abstained: bool`。把"不知道"建模成 `None` + `abstained=True` 的结构化标志，而不是一个空字符串或"抱歉"文案——否则评估层无法区分"拒答""答了个空""调用失败"。judge 调用是网络依赖，套用 Day 9 的异常分类：可重试错误与终态错误分开，judge 失败单列，不并入答错。

### Neural Garden 项目层

根据任务建立时提供的项目状态快照：Answer Generation、Citation、No-answer 判断都**尚未进入默认链路**，当前默认搜索只用 Knowledge Unit Vector Retrieval。已实现的部分里有一样东西和今天直接相关：**Relation Evidence 可回溯到 document 和 chunk**——这正是 claim 级引用校验需要的数据底座：将来答案层的每条陈述，理论上可以沿同样的方式指回具体 chunk。但记住 Day 11 的教训并移植过来：给出一个 chunk id 不等于该段落支撑该陈述，引用的有效性必须像图边一样逐条验证。

按 ROI 路线，今天知识改变的决策是：**在检索 baseline（第 1–2 步）有数字之前，不应开始生成链路**——那只会往一个测不到的黑盒里再塞一个测不到的黑盒。真要进入生成阶段，需要先建的不是 prompt，而是第二份数据集：问题 + 参考答案 + 一批标注为"库内无答案"的题。

## 最容易踩的两个坑

1. **拿检索指标上涨直接宣布产品变好。** 反例就是开头场景：Recall@5 0.72→0.85，端到端正确率可能原地不动，因为瓶颈已经移到位置效应和幻觉上。规则：每层指标只能为每层的失败作证，跨层结论需要端到端数据。
2. **以为"教会模型说我不知道"就够了。** 只加拒答不度量，会换来一个过度礼貌、什么都说不知道的系统。必须同时报幻觉率与过度拒答率，像调分类阈值一样在两者之间选工作点，而不是凭感觉要求"谨慎一点"。

## 面试官可能继续追问

**"你的 RAG 系统整体用什么指标？只用 nDCG 不行吗？"**

回答骨架：

1. 先给结论：nDCG 只证明排序层完成职责；答案层需要正确性、引用忠实度、拒答行为三套独立评估。
2. 再讲原因：检索到答案之间有四类可分离的失败（没进候选 / 进了没用好 / 编造 / 该停不停），任何单一排序指标最多覆盖第一类。
3. 落到场景：Neural Garden 当前先建 qrels 检索 baseline；生成层接入前会准备 gold answer 与不可回答题集，让每类失败都有可归因的数字，而不是靠 demo 观感。

## 合上文档前的 60 秒

今天最重要的三句话：

1. 检索指标和答案指标测的是两个失效面，不能互相顶替。
2. 引用是一条条可验证的蕴含关系，不是答案尾巴上的装饰链接。
3. 拒答是一张 2×2 混淆矩阵，幻觉率与过度拒答率都要有数字。

一个问题（60 秒内口头想过即可）：如果明天就给 Neural Garden 加答案生成，失败 A/B/C/D 四类里，你会先为哪一类设计证据、放弃哪一类的完美覆盖？
