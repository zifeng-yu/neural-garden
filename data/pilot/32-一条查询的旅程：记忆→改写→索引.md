# 一条查询的旅程：记忆 → 改写 → 索引

> 📅 2026-09-30 · 面试技术读物 · 预计阅读 14 分钟
> 抽自《四方向岗位能力矩阵》高优先级条目：Agent·5（记忆系统）、RAG·10（Query 改写）、RAG·7（向量索引）
> 三个知识点不是并列的——它们串在同一条链上：**用户说了一句话，系统怎么把它变成检索结果**。

---

## 开场：一个真实的失败场景

多轮对话里，用户第 4 轮问："**那它的价格呢？**"

一个裸奔的 RAG 系统把"那它的价格呢"六个字直接向量化、去库里搜——检索回来的是《价格法》《定价策略论文》之类的垃圾。为什么失败？三层原因正好对应今天三个主题：

1. "它"指什么？——系统没有**记忆**，不知道前三轮在聊 X 产品；
2. 就算知道，"价格"这个词和文档里写的"售价 299 元"词汇不匹配——需要**查询改写**；
3. 改写后的查询怎么在百万文档里毫秒级命中——靠**向量索引**。

下面按数据流顺序拆这三层。

---

## 第一层：Agent 记忆系统——上下文窗口是物理约束，记忆是工程解法

### 为什么必须有记忆

LLM 是无状态的：每次调用只能看见你塞进上下文窗口的东西。而对话越长，两个矛盾越尖锐——**窗口装不下**（token 上限），**装下了也贵**（每轮都重复付全文的钱）。记忆系统的本质：**把"该带的信息"在正确的时机、以压缩的形态放进窗口**。

### 三层分类（面试标准答法）

| 层 | 存什么 | 存哪里 | 生命周期 |
|----|--------|--------|---------|
| **短期记忆** | 当前对话的原始轮次 | 上下文窗口本身（+滚动截断/摘要压缩） | 会话级 |
| **长期记忆** | 历史事实、偏好、事件 | 向量库/数据库，按需检索注入 | 跨会话持久 |
| **实体记忆** | 结构化画像（用户是谁、项目状态、人物关系） | KV 存储/文档，整块注入或字段级更新 | 持久，显式更新 |

三层的写入策略完全不同：短期是**被动累积**（对话自然产生），长期是**主动抽取**（判断"这句话值得记吗"→ 摘要 → 向量化入库），实体是**更新覆盖**（"用户改用 Mac 了"要改掉旧记录，不是追加）。

### 两个必须知道的经典设计

**MemGPT 的分页隐喻**（Packer et al., 2023, arXiv:2310.08560）：把上下文窗口当"内存"、外部存储当"磁盘"，让 LLM 自己通过 function call 决定什么换入换出（`core_memory_append` / `archival_memory_search`）。操作系统虚拟内存的思想搬到 LLM 上——这个类比在面试里讲出来非常加分。

**Generative Agents 的记忆打分公式**（Park et al., UIST 2023）：检索记忆时不只看相似度，按三项加权排序：

```
score = α·recency(时间衰减) + β·importance(LLM 打的重要性分) + γ·relevance(向量相似度)
```

"上周用户说过对花生过敏"（高重要）应该压过"昨天闲聊天气"（高时近）——单靠向量相似度做不到这件事。🟢 两篇论文均为真实发表，公式为 Generative Agents 原文设计。

### 遗忘：和写入同等重要

只写不删的记忆库会退化：陈旧信息污染检索（用户半年前的偏好已失效）、相似记忆堆积。工程手段：TTL 过期、重要性衰减、**冲突检测**（新事实与旧记忆矛盾时更新而非并存）、检索频次低的降权。面试被问"记忆怎么设计"，**主动讲遗忘策略**是区分 demo 玩家和生产工程师的信号。

### 面试一句话

> "短期记忆管窗口预算，长期记忆管跨会话检索，实体记忆管结构化画像；难点不在存，在**写入判断**（什么值得记）和**检索时机**（每轮全查还是按需查）——每轮全查增加延迟和 token 成本，按需查要解决'该查的时候没查'。"

## 第二层：Query 改写——用户说的话 ≠ 该拿去检索的话

### 为什么原始 query 不可靠

三种典型失配：
1. **指代缺失**："它的价格" —— 脱离上下文无法检索（第一层记忆在这里供给上下文）；
2. **词汇失配**：用户说"电脑卡"，文档写"系统响应延迟高"——embedding 能缓解一部分，但专业术语/型号/错误码这类**精确词**，语义模型经常翻车；
3. **复合问题**："A 和 B 哪个便宜，售后哪个好"——一次检索很难同时命中两个子问题。

### 四种主流改写手段（按成本从低到高）

| 手段 | 做法 | 治什么病 |
|------|------|---------|
| **指代消解/补全** | 用 LLM 结合对话历史把 query 改写成自包含句子："X 产品的价格是多少" | 多轮对话 |
| **多路查询扩展** | 一个 query 生成 3-5 个不同表述的变体，并行检索后合并去重 | 词汇失配、表述单一 |
| **HyDE** | 让 LLM **先凭空写一篇假设答案**，用假设答案的向量去检索 | 问题-文档语义鸿沟 |
| **问题拆解** | 复合问题拆成子问题分别检索，结果汇总 | 多跳/复合查询 |

### HyDE 值得单独讲透（面试深挖高发区）

出处：Gao et al., *Precise Zero-Shot Dense Retrieval without Relevance Labels*（arXiv:2212.10496，ACL 2023）。🟢

**核心洞察**：embedding 空间里，"问题"和"答案"是两种文体，天然有距离——用户问"怎么处理缓存雪崩"，而库里存的是"缓存雪崩的解决方案是过期时间打散……"。**问题和答案不相似，答案和答案才相似。**

所以 HyDE 的做法：

```
用户 query → LLM 生成假设答案（允许胡说，不要求正确！）
          → 把假设答案向量化 → 用这个向量检索真实文档
```

假设答案哪怕事实全错也没关系——它的**文体、词汇、句式**和真实文档高度接近，向量落点就在正确文档的邻域里。这是"用生成换检索"的经典思路。

**代价与风险**（面试必须主动讲）：多一次 LLM 调用（延迟 +300ms~1s、成本翻倍）；假设答案的文体如果跑偏（比如 LLM 输出了问题形式的东西），改写反而更差。所以生产里 HyDE 通常只对"首轮检索质量差"的 query 二次触发，不是默认路径。

### 改写的工程纪律

改写是**有损操作**：改错了比不改更糟（"苹果的价格"被改写成"苹果手机的价格"，而用户其实在问水果）。所以生产系统要：保留原始 query 一起检索（改写路 + 原始路并行）、改写结果打日志可回溯、用评估集验证"改写后 recall 是否提升"。**没有评估的改写上线 = 裸奔。**

### 面试一句话

> "改写解决的是'用户的语言'和'文档的语言'之间的鸿沟。指代消解治多轮，多路扩展治词汇失配，HyDE 治问题-答案文体差，拆解治复合查询。所有改写都要过评估集，因为改写本身会引入新错误。"

## 第三层：向量索引——百万级向量上的毫秒检索

### 问题的规模

100 万条 chunk × 768 维 float32 = 约 3GB 原始向量。暴力扫描一次 query 要做 100 万次 × 768 次乘加——单机也要几百毫秒起步，且随数据量线性恶化。ANN（近似最近邻）索引用"**牺牲一点点召回率，换几个数量级的速度**"来破局。两个主流方案：

### HNSW：分层可导航小世界图（当前默认首选）

出处：Malkov & Yashunin, arXiv:1603.09320（IEEE TPAMI 2018）。🟢

**结构**：多层图。顶层稀疏（少数节点、长距离边，像高速公路），底层稠密（全量节点、短边，像市区小路）。查询从顶层入口点开始**贪心游走**——每层走到"离目标最近的局部最优"就下沉一层，直到底层做精细搜索。

**搜索时维护一个大小为 efSearch 的候选队列**：贪心不是只留一个最优点，而是保留 ef 个候选防止走进死胡同。

**三个参数就是三角权衡的旋钮**：

| 参数 | 作用时机 | 调大 → |
|------|---------|--------|
| **M** | 建索引 | 每节点连边更多：召回↑、内存↑、建索引更慢 |
| **efConstruction** | 建索引 | 建图时候选队列更大：图质量↑、建索引更慢（不影响查询速度） |
| **efSearch** | 查询 | 搜索候选队列更大：召回↑、延迟↑（唯一线上可调的旋钮） |

典型起点：M=16、efConstruction=200、efSearch=64~128，然后用自建评估集画"召回-延迟曲线"再调。🟡（经验起点值，各库文档推荐范围略有差异，必须实测）

**特点**：查询快、召回高、支持增量插入；**缺点是内存大**——图结构 + 全精度向量都要驻留内存。

### IVF-PQ：聚类粗排 + 乘积量化压缩（超大规模方案）

IVF（倒排文件）：先用 k-means 把全库向量聚成 nlist 个簇；查询时只扫最近的 nprobe 个簇——把 100 万次比较降为 100万×(nprobe/nlist) 次。

PQ（Product Quantization，Jégou et al., IEEE TPAMI 2011 🟢）：768 维向量切成 m=96 段子向量，每段用 256 个聚类中心之一近似，只存中心编号——**每向量从 3072 字节压到 96 字节，32 倍压缩**，且距离计算可以用查表加速（ADC，非对称距离计算）。

**特点**：内存极省、适合亿级；**代价是召回率通常低于 HNSW**（量化有损 + 簇边界效应），且需要训练码本、增量数据多了要重训。

### 召回-延迟-内存三角（面试的题眼）

三者不可能同时最优，选型就是选牺牲谁：

| 场景 | 选择 | 牺牲 |
|------|------|------|
| 百万级以内、内存充足、要求高召回 | HNSW（全精度） | 内存 |
| 亿级、内存紧张 | IVF-PQ | 召回 |
| 折中 | HNSW + 量化（HNSWPQ/SQ）、IVF-Flat | 视参数 |

Qdrant/Milvus/pgvector 的默认或主推索引基本都是 HNSW 系——**面试默认答 HNSW 讲清三参数，被追问超大规模再上 IVF-PQ**，这个顺序就是满分路径。

### 面试一句话

> "ANN 的本质是用可控的召回损失换数量级的速度。HNSW 拿内存换性能——多层图贪心搜索，efSearch 是线上唯一该动的旋钮；IVF-PQ 拿召回换内存——聚类缩小扫描范围，乘积量化把向量压 32 倍。选型看数据规模和内存预算，验证靠自建评估集测 recall@k 和 P99 延迟，不背参数默认值。"

## 收束：把三层串回开场那个问题

"那它的价格呢？"的完整旅程：

```
① 记忆层：检索会话记忆 → 前三轮在聊"X 产品" （实体/短期记忆供给上下文）
② 改写层：指代消解 → "X 产品的价格是多少" （必要时多路扩展出"X 售价/X 多少钱"）
③ 索引层：改写 query 向量化 → HNSW 图上游走 → top-k chunk
④ 生成层：chunk + 记忆上下文进 prompt → "X 产品售价 299 元"（带引用）
```

三层各自独立可测（记忆命中率 / 改写前后 recall 对比 / 索引 recall@k-延迟曲线），组合起来才是一个能扛多轮对话的检索系统。**面试里能把这条链完整画出来并标出每层的失败模式，就是《能力矩阵》RAG 面试凸显第 9 条"白板画完整 pipeline"的兑现。**
