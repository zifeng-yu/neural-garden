# Day 7｜从 Query 到 Top-K：一次查询如何穿过五层系统

> 日期：2026-09-14
> 预计阅读：22 分钟
> 今日只回答一个问题：用户输入一句话后，系统经历了哪些阶段才给出最终结果？

---

## 开场：事情从哪里开始失控

假设场景。

Neural Garden 的用户在搜索框里输入了一句话：

> "如何防止 SQLite 和 ChromaDB 同时写入时出现数据不一致？"

系统返回了 5 条结果。前 3 条看起来不错——标题里都有"数据一致"或"双写"字样。用户点开第一篇，发现讲的是 MySQL 主从同步；第二篇讲的是 ChromaDB 的 metadata filter；第三篇最接近，但只提到了 SQLite 事务，完全没有涉及跨存储问题。

用户关掉页面，没有留下任何反馈。

如果你是这个系统的开发者，你怎么知道它"不够好"？"前 3 条看起来不错"正是 Day 1 说过的陷阱——人工抽检几个结果不能证明检索有效。但今天我们不讨论评估方法本身，而是要追踪一条 query 从输入到输出的完整路径，看看每一层到底做了什么、没做什么。

这是第一周的综合日。我们不引入大量新术语，而是把过去 6 天学到的东西串成一条完整的链路。

---

## 先给结论

一条 query 从用户输入到最终 Top-K 结果，至少穿过五层：

1. **Query 理解层**：把用户输入转换为可检索的形式；
2. **候选生成层**（Retrieval）：从全量文档中快速召回一个粗粒度的候选集；
3. **融合层**（Fusion）：如果有多路召回，将它们的排名合并为一个统一列表；
4. **重排序层**（Reranker）：对候选集进行更精细的打分和排序；
5. **截断层**（Top-K）：取最终前 K 条返回给用户。

每一层都有明确的输入和输出。每一层都只能解决特定类型的问题。最关键的是：**每一层都不能修复上一层已经丢失的信息**。如果正确的文档在候选生成阶段就没有被召回，后面的融合和重排序无论如何也找不回它。

这个结论听起来简单，但它是整个检索系统分层调试的基础。当你发现搜索结果不好时，你需要知道问题出在哪一层，而不是盲目地调最后一层的参数。

## 事情为什么会这样

让我们用开头那条 query 走一遍完整链路。

### 第一层：Query 理解

**输入**：用户原始文本——"如何防止 SQLite 和 ChromaDB 同时写入时出现数据不一致？"

**处理**：系统可能需要做以下事情：

- 分词或 tokenize；
- 去掉停用词（"如何""时"）；
- 提取关键词（"SQLite""ChromaDB""写入""数据不一致"）；
- 生成 query embedding 向量。

**输出**：两种表示形式——

- 关键词列表：`["SQLite", "ChromaDB", "写入", "数据不一致"]`
- Query 向量：一个 768 维（或 1536 维）的浮点数数组

这一步决定了后面所有检索的"视角"。如果 query embedding 模型把"数据不一致"编码成了一个泛化的"错误处理"语义，那后面的向量检索就会偏向所有讲错误的文档，而不是专门讨论跨存储一致性的文档。

### 第二层：候选生成（Retrieval）

这一层有两条并行通道。

**通道 A：BM25（稀疏检索）**

- **输入**：关键词列表
- **处理**：对每个关键词，在所有文档的倒排索引中查找，用 BM25 公式计算每个文档的匹配分数
- **输出**：按 BM25 分数排序的文档列表，取 Top-100

假设 BM25 通道返回了 100 条候选，其中排名最高的几条都包含"SQLite"和"ChromaDB"这两个精确词。

**通道 B：Vector Retrieval（稠密检索）**

- **输入**：query embedding 向量
- **处理**：在 ChromaDB 中做近似最近邻搜索（ANN），用 cosine similarity 计算每个文档向量与 query 向量的相似度
- **输出**：按 cosine similarity 排序的文档列表，取 Top-100

Vector 通道可能返回了一些 BM25 找不到的文档——比如一篇标题是"双存储 pipeline 的失败恢复策略"的文章，全文没有出现"数据不一致"这三个字，但语义上高度相关。

**关键约束**：每条通道各自取 Top-100，这意味着如果正确答案排在第 101 位，它就永远不会被后面的层看到。这就是 Day 3 说的——**候选集决定排序器的天花板**。Recall@100 在这一层就已经确定了上限。

### 第三层：融合（RRF）

现在我们有两个排序列表，每个包含 100 条文档。它们可能重叠，也可能不重叠。我们需要一个统一的排序。

**输入**：BM25 排序列表 + Vector 排序列表

**处理**：Reciprocal Rank Fusion（RRF）

RRF 的公式很简单：

```
RRF_score(d) = Σ 1/(k + rank_i(d))
```

其中 `k` 是一个常数（通常取 60），`rank_i(d)` 是文档 `d` 在第 `i` 个列表中的排名（从 1 开始）。如果某个文档只出现在一个列表中，它只获得一项分数。

举个具体例子：

| 文档 | BM25 排名 | Vector 排名 | RRF 分数 |
|------|-----------|-------------|----------|
| Doc-A（讲跨存储一致性） | 3 | 7 | 1/63 + 1/67 ≈ 0.0308 |
| Doc-B（讲 MySQL 主从） | 1 | 45 | 1/61 + 1/105 ≈ 0.0259 |
| Doc-C（讲 ChromaDB filter） | 12 | 2 | 1/72 + 1/62 ≈ 0.0300 |

Doc-A 在两个列表中都不算特别靠前，但因为两边都有它，融合后反而排到了最前面。这正是 RRF 的价值：**被多个独立方法同时认为相关的文档，可信度更高**。

**输出**：一个统一的排序列表。我们取 Top-20 进入下一层。

**RRF 不需要训练**。它没有参数需要学习（`k` 是一个固定超参数，不是通过梯度下降学到的）。这和 Day 4 的 Learning to Rank 以及 Day 6 的 Cross-Encoder 有本质区别。

### 第四层：重排序（Reranker）

**输入**：融合后的 Top-20 候选文档 + 原始 query

**处理**：假设我们使用一个 Cross-Encoder reranker。它会把 query 和每个候选文档拼接在一起，输入一个小型 Transformer 模型，输出一个相关性分数。

与候选生成阶段的 Bi-Encoder（query 和 document 各自独立编码，然后算向量距离）不同，Cross-Encoder 会**联合编码** query 和 document，让模型看到两者的完整交互信息。这通常更准确，但也更慢。

对于我们的 query，Cross-Encoder 可能会发现：

- Doc-A 确实在讨论 SQLite 和 ChromaDB 的同时写入问题 → 高分
- Doc-B 虽然包含"SQLite"这个词，但讲的是主从同步，与 ChromaDB 无关 → 低分
- Doc-C 讨论的是 metadata filter，与"数据不一致"的语义有距离 → 中等分

**输出**：20 条文档按 reranker 分数重新排序。

**关键约束**：重排序只能改变这 20 条文档的顺序，不能引入新文档。如果真正最好的文档在融合阶段排第 21 位，重排序层永远看不到它。

### 第五层：截断（Top-K）

**输入**：重排序后的 20 条文档

**处理**：取前 K 条（比如 K=5）

**输出**：5 条最终结果，返回给用户

这一步看似简单，但它决定了一个隐含问题：如果第 5 条和第 6 条质量差距很小，截断就带有一定的任意性。在实际系统中，有时会设定一个分数阈值——低于阈值的文档即使在前 K 条内也不返回，这就是"no-answer"判断的雏形（Day 13 会详细讨论）。

```
    └─────┬──────┘

          ▼
┌─────────────────────────────┐

└─────────┬───────────────────┘
          ▼
┌─────────────────────────────┐
│  Layer 5: Top-K 截断        │
│  输入: 重排结果             │
│  输出: 5条最终结果          │
└─────────────────────────────┘
```

**每一层对应的评估指标**：

| 层 | 核心指标 | 理由 |
|----|---------|------|
| 候选生成（单路） | Recall@100 | 正确文档是否在 100 条候选中 |
| 融合 | Recall@20 | 融合后正确文档是否在前 20 条 |
| 重排序 | nDCG@20 | 重排后的排序质量（不只是"有没有"，而是"排第几"） |
| 截断 | MRR@5, Precision@5 | 最终用户看到的结果质量 |
| 全链路延迟 | P50 / P99 latency | 端到端响应时间 |

## 放回三个项目中看

### ML/DL 概念层

今天没有新概念，但过去 6 天的概念在这里第一次以完整链路的形式出现：

- **Day 1 的指标**（Recall、MRR、nDCG）现在有了具体的"挂载位置"——它们不是对整个系统的单一评分，而是分别衡量不同层的表现；
- **Day 3 的候选集天花板**在今天变成了架构图中的明确边界：BM25/Vector 的 Top-100 → RRF 的 Top-20 → Reranker 的 Top-20 → 用户的 Top-5；
- **Day 4 的 Learning to Rank**如果未来加入，会替换或补充 RRF 层——它用训练得到的权重来融合 features，而不是用固定的 `1/(k+rank)` 公式；
- **Day 5 的 BM25 与 Vector 互补**在今天的例子中有了具体表现：BM25 找到了精确匹配"SQLite""ChromaDB"的文档，Vector 找到了语义相关但用词不同的文档；
- **Day 6 的三种重排序方法**（RRF、LTR、Cross-Encoder）在今天的链路中各占一个位置：RRF 做融合，Cross-Encoder 做精排，LTR 是未来可能的替代方案。

### Python / AI Backend 工程层

这条五层链路直接影响你的代码设计：

- 每一层都是一个独立的模块，有自己的**输入 contract 和输出 contract**。比如 Reranker 的输入是 `list[SearchResult]` + `query: str`，输出是 `list[SearchResult]`（重新排序后）；
- 每一层都应该有自己的**异常处理**。如果 Embedding API 超时，Vector 通道应该返回空列表还是抛异常？如果返回空列表，RRF 会退化成只使用 BM25 的单路召回——这可能是可接受的降级策略；
- 每一层都应该是**可独立测试的**。你可以用固定的 query + 固定的文档集来测试 RRF 融合逻辑，不需要启动整个系统；
- 延迟预算需要在层之间分配。如果全链路要求 500ms 以内，那候选生成可能分配 100ms，RRF 分配 10ms，Reranker 分配 350ms，截断分配 1ms。

### Neural Garden 项目层

根据任务建立时的项目状态快照：

**已经实现的部分**：
- Knowledge Unit Vector Retrieval（对应 Layer 2 的 Vector 通道）
- ChromaDB 向量存储
- SQLite 结构化存储

**没有实现的部分**：
- BM25 通道（Layer 2 的稀疏检索）
- RRF 融合（Layer 3）
- Reranker（Layer 4）
- No-answer 判断（Layer 5 的阈值截断）
- Retrieval Evaluation 数据集和 baseline

这意味着 Neural Garden 目前只有**一层半**——Query 理解（简单的）和 Vector 单路召回，然后直接截断返回。没有融合，没有重排序，没有系统化的评估。

今天的链路图清楚地解释了为什么项目路线图中"建立 Retrieval Evaluation baseline"排在第一位：**如果你不知道当前单层 Vector 的 Recall@100 是多少，你就不知道加 BM25、加 RRF、加 Reranker 是否有意义**。也许 Vector 的 Recall@100 已经是 95%，那加 BM25 的边际收益很小；也许只有 60%，那说明大量正确文档根本不在候选集中，加 Reranker 毫无意义。

## 最容易踩的两个坑

### 坑一：把所有指标混在一起评估

一个常见的错误是：拿到最终 Top-5 结果，算一个 Precision@5，然后说"我们的系统准确率是 60%"。

问题是：60% 的 Precision@5 意味着什么？

- 可能是候选生成很好（Recall@100 = 98%），但 Reranker 排序不准；
- 也可能是 Reranker 很好，但候选生成就漏掉了一半正确文档（Recall@100 = 50%）。

这两种情况的修复方向完全不同。前者需要换一个更好的 Reranker 或加入 LTR；后者需要改进 Embedding 模型或加入 BM25 通道。

**修复方法**：分层评估。至少在候选生成之后和重排序之后各设一个评估点。

### 坑二：用同一个数据集调参和评估

假设你有一个 50 条 query 的评估集。你先跑一遍 Vector baseline，发现 Recall@100 = 72%。然后你调了 chunk size，又跑了一遍，变成 78%。你继续调 embedding 模型，变成 81%。最后你报告："我们的系统 Recall@100 = 81%。"

这是 Day 2 说过的数据泄漏。你用这 50 条 query 做了所有调参决策，这 50 条 query 就不再是独立的测试集了——它们实际上变成了验证集（validation set）。你报告的 81% 可能过拟合了这 50 条 query 的特征。

**修复方法**：至少留出一部分 query（比如 15 条）完全不参与调参，只在最终报告时使用。50 条数据确实很少，但诚实地说"我们在 15 条独立测试 query 上的 Recall@100 = 81%，置信区间较宽"，比虚假的精确要好得多。

## 面试官可能继续追问

**追问**："如果 Neural Garden 的 Vector 单路 Recall@100 很高，比如 95%，你会优先加 BM25 还是优先加 Reranker？"

回答骨架：

1. **结论**：优先加 Reranker。

2. **原因**：如果 Recall@100 = 95%，说明候选生成阶段已经很少漏文档了。加 BM25 能额外找回的 5% 文档，对最终结果的边际贡献很小。但如果当前没有 Reranker（Neural Garden 的实际情况），意味着候选集中的文档排序只依赖 cosine similarity，这通常不是最优的排序。一个 Cross-Encoder Reranker 或简单的 LTR 模型可以显著提升排序质量（nDCG），让用户在前 5 条结果中看到更相关的文档。

3. **落回项目**：但这一切的前提是先建评估数据集，验证 Recall@100 确实是 95%。如果没有评估数据，"95%"只是一个假设。Neural Garden 当前的第一步不是加任何组件，而是建 qrels 和 Evaluation Runner，用数据回答这个问题。

## 合上文档前的 60 秒

**今天最重要的三句话**：

1. 一条 query 穿过五层系统，每一层都有明确的输入、输出和能力边界；
2. 每一层都不能修复上一层已经丢失的信息——候选生成决定天花板；
3. 分层评估才能定位问题，混合评估只能告诉你"不好"但不能告诉你"哪里不好"。

**60 秒口头思考**：

如果 Neural Garden 的用户搜索"Concept 归一化用了什么策略"，而你的知识库中有一篇文档详细记录了 Concept 归一化的实现细节，但这篇文档的标题是"实体消歧流程"——你觉得这条 query 在当前只有 Vector 单路的系统中，能召回到这篇文档吗？如果不能，问题出在哪一层？
