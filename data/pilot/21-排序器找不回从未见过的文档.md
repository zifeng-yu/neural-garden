# Day 3｜排序器很聪明，但它找不回一份从未见过的文档

> 日期：2026-09-10
> 预计阅读：22 分钟
> 今日只回答一个问题：Retriever 和 Reranker 的职责边界在哪里，为什么候选集一旦丢失了正确文档，后面无论怎么排序都无法弥补？

## 开场：事情从哪里开始失控

假设场景。你的 Neural Garden 里存了一篇关于"数据泄漏"的知识单元，标题是"同一份标注用了两次就作废"。用户在搜索框里输入："评估检索系统时，调参和测试用同一批数据会怎样？"

你当前的检索链路是：用户查询 → Embedding → ChromaDB 向量检索 → 返回 Top-10 → 直接展示。

你发现 Top-10 里排第一的是一篇关于"测试集划分"的文章，排第三的才是目标文章。于是你决定加一个 Reranker（重排序器，对候选文档重新打分排序的模型）。加完之后，目标文章从第三名升到了第一名。你很高兴，记录："引入 Reranker 后，搜索质量显著提升。"

但你的同事试了另一个查询："为什么 Recall@K 比 Precision 更适合评估检索？"这次，目标文章根本不在 Top-10 里——向量检索就没有把它召回。Reranker 拿到的 10 篇文档全是关于 Precision 和 F1 的，没有一篇讨论 Recall@K 的适用场景。Reranker 在这 10 篇里认真排了一遍，选出了一篇"最不差"的，但用户一眼就看出这不是他要的东西。

问题出在哪？不是 Reranker 不够好。是 Reranker 从始至终就没见过正确文档。

## 先给结论

一个检索系统至少有两个截然不同的阶段：**候选生成**（candidate generation，从海量文档中快速筛出一个小集合）和**候选排序**（candidate ranking，对小集合精细打分重新排列）。Retriever 负责前者，Reranker 负责后者。它们的职责不同，约束不同，失败的后果也不同。

Retriever 的失败是**不可逆的**：如果正确文档没有进入候选集，Reranker 无论多精确都无法把它找回来。这是因为 Reranker 的输入是且仅是 Retriever 的输出——它没有能力回到全量文档库中重新搜索。就像面试官只能在收到的简历里选人，如果某位候选人的简历从来没有投递进来，面试官再厉害也无法录用他。

因此，评估一个检索系统时，**Retriever 用 Recall 类指标**（衡量正确文档有没有被召回），**Reranker 用排序质量指标**（衡量正确文档被召回后有没有排到前面）。混在一起评估，你分不清是候选集不够还是排序不够好。

## 事情为什么会这样

让我们沿着数据流走一遍。

**第一步：Retriever 生成候选集。** 用户查询被编码成向量，与 ChromaDB 中所有文档向量计算相似度，取 Top-K 返回。K 通常设为 10、20 或 50。这一步的核心约束是**速度和规模**：你的知识库可能有数万甚至数百万个 chunk，Retriever 必须在几十毫秒内完成筛选。向量检索（也叫 Dense Retrieval，用稠密向量的余弦相似度做检索）和 BM25（基于词频的稀疏检索）都是常见的 Retriever 实现。

Retriever 的输出是一个**候选集**（candidate set），比如 20 篇文档。这个集合的质量用 **Recall@K** 来衡量：在所有相关文档中，有多少出现在了这个 Top-K 里？

假设你的知识库里对某个查询有 3 篇相关文档。Retriever 返回 Top-20，其中包含了这 3 篇中的 2 篇。Recall@20 = 2/3 ≈ 0.67。那篇没被召回的文档，从这一刻起就彻底退出了本次搜索流程。

**第二步：Reranker 重新排序。** Reranker 拿到这 20 篇候选文档，对每一篇和用户查询做更精细的匹配打分。Cross-Encoder 是一种典型的 Reranker 模型——它把查询和文档拼接在一起送入 Transformer，输出一个相关性分数。这比 Retriever 的双向量点积（Bi-Encoder 方式，查询和文档分别编码后计算相似度）要慢得多，但精度更高。

Reranker 的输入是 20 篇，输出还是 20 篇——**只是顺序变了**。它不会引入新文档，也不会去全量库里搜索遗漏的文档。如果那篇丢失的文档对回答用户问题至关重要，用户将永远看不到它。

**这就是职责边界：**

| 阶段 | 输入 | 输出 | 能解决什么 | 不能解决什么 |
|------|------|------|-----------|-------------|
| Retriever | 全量文档库 + 查询 | Top-K 候选集 | 从海量中快速缩小范围 | 精细排序 |
| Reranker | Top-K 候选集 + 查询 | 重排后的 Top-K | 在候选集内提升排序质量 | 找回未进入候选集的文档 |

**一个具体的数字例子：**

假设知识库有 10000 个 chunk。查询 q 的相关文档是 {d3, d47, d892}。

场景 A：Retriever 返回 Top-20，包含 {d3, d47}，不包含 d892。
- Recall@20 = 2/3 ≈ 0.67
- Reranker 对 20 篇重排，d47 排到第 1 位，d3 排到第 5 位
- MRR（Mean Reciprocal Rank，第一个相关结果的排名倒数的均值）= 1/1 = 1.0
- 表面看排序质量很好，但 1/3 的相关文档永远丢失了

场景 B：Retriever 返回 Top-20，包含 {d3, d47, d892}，全部召回。
- Recall@20 = 3/3 = 1.0
- 但 d892 排在第 18 位，d3 在第 12 位，d47 在第 7 位
- Reranker 重排后：d47 第 1 位，d3 第 2 位，d892 第 3 位
- MRR = 1/1 = 1.0，且所有相关文档都在结果里

场景 A 的 MRR 和场景 B 一样，但场景 A 丢了 1/3 的相关文档。如果你只看排序指标，你会以为系统没问题。**Recall 和排序质量必须分开看。**

## 把系统画出来

```
用户查询: "评估检索系统时，调参和测试用同一批数据会怎样？"
    │
    ▼
┌─────────────────────────────────────────────────┐
│           Retriever（候选生成）                    │
│  输入: 查询向量 + 全量文档库 (10000 chunks)        │
│  方法: 向量相似度 / BM25                          │
│  速度: ~10ms                                     │
│  输出: Top-20 候选集                              │
│                                                   │
│  评估指标: Recall@K                               │
│  ❌ 如果正确文档不在 Top-20 → 永久丢失             │
└───────────────────────┬─────────────────────────┘
                        │ 20 篇文档
                        ▼
┌─────────────────────────────────────────────────┐
│           Reranker（候选排序）                     │
│  输入: 20 篇候选 + 查询                           │
│  方法: Cross-Encoder / LTR / RRF                 │
│  速度: ~200ms（20篇 × ~10ms/篇）                  │
│  输出: 重排后的 Top-20                             │
│                                                   │
│  评估指标: MRR, nDCG, Precision@K                 │
│  ❌ 无法找回 Retriever 遗漏的文档                  │
└───────────────────────┬─────────────────────────┘
                        │
                        ▼
                   展示给用户
```

**关键观察：** 两个阶段之间是一条单向管道。候选集一旦确定，就只能缩小（排序），不能扩大（补充新文档）。

## 放回三个项目中看

### ML/DL 概念层

在 Day 1 和 Day 2 中，你已经见过 Recall@K、MRR 和 nDCG。今天的核心认识是：**这些指标不应该混在一起报告**。Recall@K 衡量的是 Retriever 的能力——"正确文档有没有进入候选集"。MRR 和 nDCG 衡量的是排序器的能力——"进入候选集后，正确文档有没有排到前面"。

后续你还会学到 XGBoost 与 Learning to Rank（Day 4）、BM25 与 Vector 的互补性（Day 5），以及 RRF 和 Cross-Encoder 的职责边界（Day 6）。它们都和今天的候选集边界直接相关：有的用来生成候选集，有的用来重排候选集，混淆它们的角色会导致你无法定位系统失败。

### Python / AI Backend 工程层

这个两阶段结构会直接影响你的代码 contract 设计。Retriever 和 Reranker 应该有**不同的输入输出类型**，而不是共享一个模糊的 `search()` 函数。

```python
from dataclasses import dataclass

@dataclass
class RetrievedDoc:
    doc_id: str
    score: float          # Retriever 给的相似度分
    content: str

@dataclass
class RerankedDoc:
    doc_id: str
    retrieval_score: float
    rerank_score: float   # Reranker 给的分数
    content: str

class VectorRetriever:
    def retrieve(self, query: str, top_k: int = 20) -> list[RetrievedDoc]:
        """从全量库中召回候选集。"""
        ...

class CrossEncoderReranker:
    def rerank(self, query: str, candidates: list[RetrievedDoc], top_k: int = 5) -> list[RerankedDoc]:
        """对候选集重排序。注意：输入是 candidates，不是全量库。"""
        ...
```

这种类型区分不只是代码风格问题。它让你在写测试时可以分别验证：Retriever 的 Recall@K 是否达标，Reranker 的 MRR 是否在候选集质量给定的情况下有所提升。如果两个阶段共享同一个接口，你很容易写出一个"端到端搜索测试"，却无法定位失败发生在哪个阶段。

### Neural Garden 项目层

根据任务建立时的静态快照，Neural Garden 当前的默认搜索链路**只有 Knowledge Unit Vector Retrieval**——也就是说，只有 Retriever，没有 Reranker。这意味着：

- 当前的搜索质量上限完全取决于向量检索的 Recall@K；
- 如果你观察到某些查询返回的结果"不太对"，你需要先判断是向量检索没有召回正确文档（Recall 问题），还是召回了但排序不好（排序问题）；
- 尚未实现的 BM25、Hybrid Retrieval、RRF 和 Reranker 都是候选生成或候选排序阶段的改进；
- 在做任何改进之前，你需要 Day 2 中讲到的评估基线来证明改进是否真的有效。

**当前已实现：** 向量检索、SQLite 存储、ChromaDB 向量存储。
**当前未实现：** BM25、RRF、Reranker、Learning to Rank、Graph Retrieval。
**决策点：** 是否加入 Reranker 取决于向量检索的 Recall@K 是否已经足够高——如果候选集本身就经常丢失正确文档，优先提升 Retriever（比如加入 BM25 做 Hybrid），而不是先加 Reranker。

## 最容易踩的两个坑

**坑一：只看 MRR 不看 Recall，以为系统没问题。**

MRR 衡量的是"第一个正确结果的排名"。如果 Retriever 恰好把正确文档召回了，Reranker 把它排到第一位，MRR = 1.0。但如果另外 40% 的查询中正确文档根本没有进入候选集，这些查询的 MRR 可能也很低，但你会习惯性地说"平均 MRR 还不错"。正确的做法是**先报告 Recall@K，再报告 MRR 和 nDCG**，这样你才能分清"有多少查询能成功"和"成功的查询排得好不好"。

**坑二：Top-K 设得太小，然后用 Reranker 来"补偿"。**

K=5 意味着 Retriever 只返回 5 篇文档。如果正确文档排在第 6 位，它就永远不会被 Reranker 看到。有些人会加一个强力的 Reranker，期望它"弥补"Retriever 的不足。这是不可能的——Reranker 只能在你给它的文档里排序，不能创造新文档。正确做法是**适当放大 Retriever 的 K 值**（比如 K=20 或 K=50），确保 Recall 足够高，然后用 Reranker 从这 20-50 篇中选出最好的 5 篇展示给用户。

## 面试官可能继续追问

**追问：** "你的 Neural Garden 目前只有向量检索，没有 Reranker。你怎么知道当前结果不好是因为缺少 Reranker，而不是因为向量检索本身就不行？"

**回答骨架：**

1. **结论：** 需要先做分层评估——先用 Recall@K 衡量向量检索的候选集质量，再看是否存在"正确文档在候选集中但排序不对"的情况。
2. **原因：** 如果大部分失败查询中正确文档根本不在 Top-K 里，说明瓶颈在 Retriever 阶段，加 Reranker 不能解决问题。如果正确文档在候选集中但排名靠后，才是 Reranker 能改善的场景。
3. **落到项目：** 我会用 Day 2 建立的评估基线，对每个失败查询标注"正确文档是否在 Top-20 中"，统计 Recall@20。根据这个数字决定优先改进 Retriever 还是引入 Reranker。

## 合上文档前的 60 秒

**今天最重要的三句话：**

1. Retriever 决定候选集的上限，Reranker 只能在这个上限之内优化排序。
2. 正确文档没进入候选集 → Retriever 的失败，不可逆；正确文档进入了但排名低 → Reranker 可以改善的问题。
3. 评估时必须分层：先 Recall@K（候选集够不够），再 MRR/nDCG（排序好不好）。

**口头思考题：** 如果 Neural Garden 的向量检索 Recall@20 是 0.6，而加入 BM25 后 Recall@20 提升到 0.85——这个提升是在改善 Retriever 还是 Reranker？它改变的是哪个阶段的天花板？
