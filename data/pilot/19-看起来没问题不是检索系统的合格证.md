# Day 1｜"看起来没问题"不是检索系统的合格证

> 日期：2026-09-08
> 预计阅读：20 分钟
> 今日只回答一个问题：为什么"我试了几次，挺准的"不能证明检索有效，以及为什么 Neural Garden 的下一步是评估，而不是继续堆功能？

## 开场：事情从哪里开始失控

假设场景。一次项目评审，你给同事演示知识库搜索：输入"试用期员工请假流程"，第一条结果就是目标片段。同事点头："检索能用了吧？接下来把 BM25、Reranker 加上，再接个图谱，就完整了。"你觉得有道理，开始排两周后的功能计划。

两周后，一位用户问"去杭州的租房补贴标准"，系统返回十条泛泛的租赁合同内容。你换了 embedding 模型，结果"好像"变好了；又一位用户查"照片被商用怎么索赔"，还是找不到。这时你才发现：你根本说不清上次换模型是修复了问题，还是把问题挪到了你没看的地方。

失控的源头不是那两次失败，而是从一开始，你就没有任何办法描述这个系统的整体状态。

## 先给结论

问题不在于"试了是对的"没有价值，而在于它能证明的范围太窄。你现场试的那几条查询，几乎必然是你记得知识库里有答案、措辞规范、语义直接的查询——它们是对现有链路最友好的样本。它们全部命中，与系统整体召回很差，完全可以同时成立。

能替代这种感觉的，只有一种东西：可重复的评估基线（evaluation baseline，简称 baseline，指一个固定的、之后再比较变化时都参照的起点状态）。它由三个部件组成：一组固定的查询集（eval set）、一份标注"每条查询应该命中哪些文档"的清单（在信息检索领域叫 qrels，即 query relevance judgments，查询相关性判定）、一个可以随时重跑的指标计算脚本。有了它，任何改动——换分块策略、换 embedding 模型、加 Reranker——的结果都是一组可比较的数字，而不是一种印象。

对 Neural Garden 而言，结论很直接：当前最优先的下一步不是 BM25，不是 Hybrid，而是给已有的向量检索建立基线。因为在一个没被测量过的系统上，任何"改进"都无法归因，任何对外报告的数字都无法辩护，任何退化也无法拦截。

## 事情为什么会这样

用一个具体例子把因果链走完整。

假设知识库有 1000 个 chunk，你手写 20 个真实问题，并为每个问题翻遍库标注了相关 chunk——这组"query → 相关文档"对就是 qrels。现在向量检索器对每条查询返回 Top-10，你统计每组相关文档有多少进了 Top-10，得到 Recall@10。

结果长这样：20 条查询里，15 条常规查询（问流程、问概念）的 Recall@10 是 0.8；剩下 5 条"困难查询"——含错误码、产品代号、政策条款原话的——Recall@10 是 0.2。整体约 0.65。

演示时你只会试前者。原因不是故意作弊，而是结构性盲区：你只可能基于"你知道库里有什么"来构造查询，库里缺了什么、哪种表述方式 embedding 处理不了，你根本不知道，也就不会测到。幸存者偏差不仅作用于成功案例，也作用于测试样本的选择本身。

然后用户炸了，你换 embedding 模型。新模型"看起来"更好——依据是什么？如果只是重跑那三条熟悉查询，结论毫无信息量。若重跑 20 条查询加 qrels 脚本，你可能会看到：常规组从 0.8 升到 0.85，困难组从 0.2 掉到 0.15。整体涨了，体验跌了。没有基线，这类静默回归（silent regression：指标或行为变差但无人察觉地进入新版本）根本无法察觉，直到下一次用户投诉替你"完成评估"。

这个例子里还藏着一个更根本的事实：检索是一条流水线，chunking、embedding、Top-K、fusion、rerank 每一层都有自己的失败模式，而"结果不好"只是末端症状，不告诉你哪一层病了。每一层的指标都只能在冻结的查询集和标注上计算。所以评估的本质不是"给系统打个总分"，而是让每一层可测、让每一次改动可归因。

常见的反驳是：标注太贵，知识库天天变，值得吗？值得，因为规模远小于想象：对个人知识库，30～50 条手写查询加人工判定，一个下午能完成一套初始版本，之后每次流水线变更前重跑。真正贵的，是每次失败后毫无根据的两周瞎调。

```
      │ chunk → embed → top-K (→fusion→rerank)   │
      └───────────────────┬──────────────────────┘

      ┌───────────────────▼──────────────────────┐
      │ 指标脚本：Recall@K / MRR / nDCG          │
      │ 按查询分组，不只输出总分                  │
      └───────────────────┬──────────────────────┘

```

## 放回三个项目中看

### ML/DL 概念层

你在 ML/DL 项目 Day 5 学过 train/validation/test 与 data leakage；今天这套东西是同一纪律在检索系统上的翻版：eval set 相当于系统的 test set，用来判断"改动是否有效"，而不是拿来反复调参后再对外汇报。而 Recall@K、MRR、nDCG 正是 Day 2 手工算过的那组指标——今天它们从练习题进入真实流水线。

### Python / AI Backend 工程层

评估本质上是一个函数：输入（查询集、qrels、被测系统），输出（指标字典）。一旦它是函数，工程手段就全部适用：评估数据集放进版本控制（JSONL 文件入 git，而不是散落在聊天记录里）；指标计算是纯函数，用 pytest 验证；一次变更跑 v_old 与 v_new 各一遍，输出 diff 报告。这和后端"准备数据集、跑代码、断言结果"的回归测试是同一件事，只是被测对象从函数变成了整条检索链路。

### Neural Garden 项目层

根据任务建立时提供的项目状态快照：Knowledge Unit 向量检索已进入默认搜索链路；BM25、RRF、Reranker 均未进入；本地测试基线 54 项通过——请注意，那 54 项验证的是代码行为正确，没有一项能回答"检索命中率高不高"。快照同时明确写着：当前没有可量化的 Retrieval Evaluation baseline。所以最高 ROI 路线的第一项才不是任何检索新功能，而是"版本化评估数据集 + qrels + 指标脚本 + 向量 baseline"。之后要不要上 Hybrid，判定证据也来自这里：如果困难组查询（关键词精确匹配类）的 Recall 显著低于语义类，BM25 补位才有依据；反之就是白加一层复杂度。

## 最容易踩的两个坑

**坑一：用自己记得的查询测试。** 自检标准：查询集里是否包含"预期系统处理不好"的类别——错误码、专有名词、口语化缩写、政策原话。没有，这套评估集就是装饰品。补救数据来源：Neural Garden 快照显示 Search Session 和 Feedback Event 已经在记录，但尚未被消费——真实失败查询就躺在那里，这是它们第一个该发挥作用的场景。

**坑二：用同一批查询既调参又汇报。** 看着失败案例调 chunk size、改 Top-K，数字涨了，宣布改进。这个过程中查询集已经从"测量工具"退化成"训练信号"，汇报数字失去独立性——像提前给学生划考题再宣布教学质量提升。分离办法是明天的主题。

## 面试官可能继续追问

**"你的评估集只有 20 条查询，这些指标可信吗？"**

回答骨架：

1. 先给结论：小样本下指标的统计精度有限，但它的用途本来就不是对外宣称性能数字，而是回归防护和失败归因——有证据比没证据强一个量级。
2. 再解释原因：估计方差随样本量增大而缩小，20 条查询上几个百分点的波动属于噪声；对策是看分组指标（按查询类型拆分）、看逐查询 diff 而不是只看总分，并且每次出现新失败模式就向评估集追加一条。
3. 落到项目：「Neural Garden 我会从 30 条起步，把评估集当活资产持续扩充，但汇报任何结论时都会附带样本量和它的局限。」

## 合上文档前的 60 秒

今天最重要的三句话：

- 你挑来试的查询永远偏向系统擅长的方向，所以"看起来不错"不具备任何反驳能力。
- 评估基线 = 冻结查询集 + qrels + 可重跑的指标脚本，缺一项，改动就无法归因。
- 对 Neural Garden，向量检索 baseline 是接下来一切功能决策的前置条件。

一个口头思考题：那"54 项测试通过"里，有没有哪怕一项，能回答"用户搜 X，系统会不会返回正确的文档"？
