# Day 12｜向量找回"像的"，图找回"连的"：但 GraphRAG 的价值要拿实验说话

> 日期：2026-09-19
> 预计阅读：22 分钟
> 今日只回答一个问题：图检索在什么时候才真的给搜索系统带来正收益？怎样证明，而不是感觉？

## 开场：事情从哪里开始失控

【假设场景】一场设计评审。有人提议给知识库项目加一个图检索模块，举的例子很有说服力：用户问"P1 文档里的缓存策略和 P3 的一致性假设有没有冲突？"——答案散落在三份文档里，向量搜索确实召不全。会议室纷纷点头，方案几乎要通过，直到角落有人问了三个问题："加图之后，预期在哪一类查询上提升多少？你现在的向量 baseline 是多少？如果加了图总体指标反而降了，你怎么知道该回滚哪一层？"全场安静。因为大家意识到：刚才比的不是两个技术方案，而是"有证据的判断"和"没有证据的直觉"。

## 先给结论

图可能值钱，是因为它改变了问题的形状。向量检索解决的是"问法和答法措辞不同，但意思相近"；图遍历（traversal，沿边扩展）解决的是"答案不在任何单篇文档里，而在文档之间的关系路径上"。这是两类问题，不是同一类问题的两个难度档位。

但图的收益有前提：图上的边必须是真实的。当边是 LLM 抽取出来的，每一跳都在引入错边概率，多跳之后误差按乘法累积。所以图的净效果 = 可达性增量 − 噪声放大，这个减法只能量出来，不能想出来。

证明图价值的唯一途径是对照消融实验（ablation，关掉某个组件跑同一套评估）：同一 query 集、同一 qrels，开图与不开图各跑一遍端到端检索评估，并且按问题类型拆开看，不只看总平均。没有 baseline 之前，加图不是功能，是赌博。

## 事情为什么会这样

拆开评审会上那个问题。假设知识库里有三个片段：

- c102：「P1 的写缓存采用延迟双删，间隔 30 秒」
- c178：「P3 的读路径依赖本地内存缓存，失效最长 60 秒」
- c203：「评审纪要：延迟双删只对单库生效，与本地缓存的假设冲突」

向量检索做的是成对比较：query 对每个 chunk 算一次余弦相似度，取 Top-K。query 里高频出现"缓存、一致性、冲突"，很容易召回一堆泛泛的缓存科普文；c102 和 c178 各自与 query 的相似度都不高，真正点题的 c203 却可能只回来一条。关键信息是分布式的，而相似度不会累加——A 与 query 像、B 与 A 有关，不代表检索器"知道"要把 B 捎上。Bi-Encoder 把每篇文档压成空间里一个孤立的点，点没有邻接，路径无处存放。

图的解法是"捎上"。query 先做实体归一化，在图中锚定一个种子节点（seed node，遍历的起点，比如"延迟双删"），然后做一两跳遍历收集子图（subgraph）：c102 的"延迟双删"与 c178 的"本地缓存"，通过 c203 记录的关系连在一起，三个片段连同 Relation Evidence 一起成为候选。看起来正是问题想要的。

但注意"通过关系连在一起"这个说法。这些边是 LLM 从文本抽取的推断，不是被世界确认过的事实。假设抽检显示单跳边的 precision 约为 90%（演示数字，非项目实测），在误差独立的假设下，两跳路径整体正确的上限约为 0.9 × 0.9 = 81%；更糟的是误差会伪装——一条错边若把两个本不相关的概念子树嫁接上，沿它遍历到的一切都"看起来很合理"。跳数越多，可达性越强，路径可信度越低。这就是今天唯一的主因果链：答案分布在路径上 → 成对相似度看不见路径 → 图显式存关系、可遍历 → 但关系是抽取的 → 抽取误差随多跳累积 → 图的净值正负，只能实验说了算。

所以图在什么时候真有价值？查询本身带关系形状时：多跳推理（A 依赖 B，B 与 C 冲突）、聚合类（围绕某概念的全部提及）、实体约束（同名的人或系统要分开）、需要证据路径（要向用户展示推理链）。什么时候只是增加复杂度？绝大多数问题是单文档可答的事实题；概念归一化不稳、合并出错，图"连得越多错得越多"；边没有证据，查出来也不敢用。微软的 GraphRAG 论文定位就是例子：它针对的是对整个语料的"查询聚焦摘要"——回答"这批材料的主要主题是什么"这类全局问题——而不是把所有检索场景都变聪明的银弹。

## 把系统画出来

```
              Query「P1 缓存策略与 P3 一致性是否冲突?」
                          │
          ┌───────────────┴───────────────┐
          │                               │
    Vector / BM25                    实体归一化
    成对相似度, 各取 Top-K            锚定 seed node
          │                               │
    候选列表 A                       1~2 跳遍历
          │                          收集子图+证据
          │                               │
          └───────────────┬───────────────┘
                          │
               union + 去重 → 重排 → Top-K
                          │
                     Generator

     失败点(左路):                 失败点(右路):
     措辞不同 → 漏召               错边 → 整条路径错
     信息分布多文档 → 连不上        hub 节点 → 子图爆炸
                                   误差随跳数累积
```

| 维度 | 向量检索 | 图遍历 |
|---|---|---|
| 判断单位 | (query, doc) 相似度 | (节点, 关系, 节点) 与路径 |
| 答案位置 | 单篇文档内 | 文档之间的连接上 |
| 信号来源 | embedding 空间成对比较 | 离线抽取并存储的边 |
| 典型失败 | 措辞差异导致漏召 | 边错误导致路径跑偏 |
| 运行成本 | 一次向量查询 | 一次锚定 + 每跳邻域扩展 |

## 放回三个项目中看

### ML/DL 概念层

Day 4 学过 Bi-Encoder 与 Cross-Encoder：前者把文本各自压成点，只能表达成对相似——这正是"向量看不见路径"的数学根源。图提供的是显式结构，和 BM25 的词汇信号一样，是对向量空间的类型互补。后面的路线里还会遇到两个容易混淆的概念：Graph Embedding 仍然是把节点压成向量，本质还是成对相似度，只是"结构像"也算相似；GNN 用邻域聚合更新节点表示，相当于让邻居信息改变节点自身。两者改变的都表示，不改变证据——只有显式边加 Relation Evidence 才能回答"这条候选为什么被带进来"。

### Python / AI Backend 工程层

图进入搜索链路后，一次请求从"一次 embedding + 一次向量查询"变成"一次锚定 + N 次邻域扩展"，每一跳都是时延和失败源，而 hub 节点（高度数的概念节点，比如"系统""数据"）可能一次炸出上千邻居。contract 必须圈定爆炸半径：

```python
@dataclass
class GraphRetrievalConfig:
    max_hops: int = 2              # 限制多跳深度, 控制误差累积
    max_nodes: int = 50            # 限制子图规模, 防 hub 节点爆炸
    require_evidence: bool = True  # 无证据回溯的节点不进上下文
    timeout_ms: int = 300          # 图扩展整体时间预算
```

还有 Day 10 的回响：遍历时若发现某条边指向的概念在 SQLite 里已不存在，这不是"查空"，是数据完整性事故，应记录并触发 reconciliation，而不是静默跳过。

### Neural Garden 项目层

根据任务建立时提供的项目状态快照：Concept 提取与归一化、Concept Relation、可回溯到 document/chunk 的 Relation Evidence 已实现；NetworkX MultiDiGraph 在运行时从 SQLite 构建，不是持久化事实源；Graph-Augmented Retrieval 没有进入默认搜索链路，当前默认只有 Knowledge Unit 向量检索。这正好解释了为什么 ROI 路线把"评估 Evidence-backed Graph Retrieval"排第七，在评估基线、Hybrid、Reranker 之后——不是图不重要，是它还没被证明有用，而项目当前连可量化的 retrieval baseline 都没有，"有没有用"这个问题现在根本无法回答。推进它所需的证据：① 从版本化评估集中单独切出一组多跳/聚合型 query；② 同一 qrels 下跑"向量 baseline"与"向量+图"的 ablation；③ 分意图看 Recall@K、nDCG 和 latency，不只看总平均；④ 人工抽检图命中路径的 evidence 链是否成立。在这组数据存在之前，简历上"构建知识图谱"只能是事实陈述，不能是效果声明。

## 最容易踩的两个坑

**坑一：把"图建好了"当成"GraphRAG 成立了"。** 一条边存在于图上，只证明"LLM 在某次抽取中认为某关系可能出现"，不证明关系为真，更不证明它对当前查询有用。三层论断各不相同，混着说，面试追问一个"precision 多少"就会现形。

**坑二：只用全局平均指标评估图，然后得出"图没用"。** 图针对的本来就是少数问题形态——即使它在多跳子集上大幅提升，稀释进总平均后可能趋近于零；反过来它对简单事实题引入的噪声和时延，也可能让总指标小幅下跌。只报全局数字，两种情况下你都会做出错误决策。正确结论的形态是："图对多跳类查询是 +12 个点，对单文档事实题是 −2 个点且增加一跳延迟，所以按意图路由"——而不是笼统的有用/没用。

## 面试官可能继续追问

"你项目里有知识图谱，你怎么证明它给检索带来了正收益，而不是自我感动？"

回答骨架：
1. 先给结论：没有分型评估和 ablation 之前，我不敢声称图有收益，这也是我把它排在评估基线之后的原因。
2. 解释方法：同一版本化 query 集与 qrels，开图/不开图各跑一遍端到端评估，多跳子集单独报 Recall@K 与 nDCG，另加时延和边证据的人工抽检。
3. 落到项目：关系抽取和证据回溯层已实现、图在运行时从结构化存储构建，但评估基线在建，所以我会说"图检索是待验证的候选能力"，不会说"已实现 GraphRAG、效果更好"。

## 合上文档前的 60 秒

今天最重要的三句话：
- 向量解决"相似"，图解决"相连"，它们是两类问题的形状。
- 图的每一跳既带来触达答案的机会，也带进一条可能错误的边，误差按跳数放大。
- 证明图价值的唯一货币，是分型 query 集上的 ablation 实验。

一个 60 秒的口头问题：你的知识库收到的真实提问里，有多大比例必须跨文档连接关系才能回答？如果连 5% 都不到，最先该建的到底是图，还是别的什么？
