# Day 9｜请求超时了，对面可能已经执行完了

> 日期：2026-09-16
> 预计阅读：约 20 分钟
> 今日只回答一个问题：一次外部调用失败之后，哪些信息决定了你该重试、能重试、以及失败了该留下什么？

## 开场：事情从哪里开始失控

**假设场景**（以下两起事故均未真实发生，但制造它们的代码非常真实）。

一条定时任务在更新知识库：对某文档切出的 200 个 chunk 逐个调用 Embedding API 并写入向量。第 76 个请求，连接建立正常，但 30 秒没有收到任何响应字节——读取超时。代码里写的是：

```python
except Exception:
    return None
```

函数"正常"返回了，这批任务被标记为已处理。三周后，有用户反馈这篇文档的内容搜不到。翻遍日志：零条报错。因为每一条错误都在产生的那一刻被 `return None` 抹掉了。这是事故一。

事故一曝光后，开发者加上了重试：失败最多试三次。某天夜里网络抖动，一条"写入向量"的 POST 请求在服务端**已经执行成功**，只是响应包丢在了回程路上。客户端只看到超时，于是重试两次——同一个 chunk 写进了三份向量。检索结果里出现三个近乎相同的条目，去重逻辑开始背锅。这是事故二。

两起事故表面相反——一个失败太少，一个重试太多——但根源是同一件事：**写这段代码的人，把"超时"当成了一种错误，而它其实是两种完全不同的现实。**

## 先给结论

第一，超时只说明"你不知道结果"，不说明"失败发生了"。连接超时（connect timeout）意味着请求大概率根本没到达对方；读取超时（read timeout）意味着对方可能已经完整执行了写操作，只是回执没能送回来。同一个 `Timeout` 异常之下，藏着两个世界。

第二，所以"能不能重试"不是胆量问题，而是两个事实的函数：错误发生在请求生命周期的**哪个阶段**（决定对面状态是什么），以及这个操作**是否幂等**（决定重复执行会发生什么）。读超时之后敢不敢重试 POST，取决于你有没有用稳定 id 做 upsert，而不是取决于重试次数设成 3 还是 5。

第三，异常处理的第一职责是**保住现场**，不是维持表面平静。把失败压成 `None`，不是把失败变成成功，而是把一个可诊断的失败变成一个不可见的失败——它会以缺向量、脏数据、指标悄悄劣化的形式，在几周后的检索结果里重新出现。

## 事情为什么会这样

按顺序走一遍一条请求的时间线。以 Python 最常用的 `requests` 库为例，`timeout` 参数可以传一个元组 `(connect, read)`，两个数字管理的是两件不同的事：**connect** 是建立 TCP 连接的等待上限——对方服务挂了、域名错了、网络不通，会在这里死掉；**read** 是"每两次收到字节之间"的等待上限，官方文档特意强调它**不是整个下载的总时限**——只要服务端每隔不到 read 秒吐一点数据，永远不会触发。如果只传单个值，它会同时用作 connect 和 read；如果不传，默认**无限等待**。最后这一点就足够解释很多"服务没报错但整个管道卡死"的悬案。

连接阶段失败，请求没有送达，对面什么都没发生——重试是安全的。读取阶段超时呢？想象你对一个 LLM API 设了 10 秒超时，而它正在生成一段 600 token 的回答：超时的这一刻，请求已经在对面被完整接收，token 可能正在被计费，结果可能已经写进了某个存储。客户端单方面挂断了电话，不代表对面的事没办完。

区分了阶段之后，错误可以按"对面还欠不欠我们一次执行"分成两类，工程上常称 **retryable error（可重试错误）** 与 **terminal error（终止性错误）**：

- **可重试**：连接建立失败、读取超时、429 Too Many Requests、502/503/504 这类网关与临时过载错误。语义是"现在不行"或"结果未知"，再试有可能成功。其中 429 常带 `Retry-After` 头——HTTP 标准里让服务端直接告诉你等多久，尊重它比自作聪明更可靠。
- **终止性**：400 参数错误、401/403 鉴权失败、404 资源不存在。这类是**你这边的问题**，重试一万次结果不变，应该快速失败、大声报警。对它们重试不但无用，还会淹没真实信号、消耗配额。

对可重试错误直接匀速连打三次也是错的：如果失败原因是服务端过载，全客户端同一秒失败，就会在同一秒集体重试，把刚喘过气的服务再次打死。标准做法是**指数退避加随机抖动**（exponential backoff with jitter）：等待 1 秒、2 秒、4 秒地翻倍，再叠一个随机量把重试时刻打散。

然后是重试安全的核心：**幂等（idempotency）**——同一请求执行一次和执行 N 次，效果完全相同。GET 查询天然幂等，随便重试；"写入向量"不天然幂等，要靠设计：给每个 chunk 一个确定性 id（比如 `hash(doc_id + chunk_seq)`），写入用 upsert 语义（同 id 覆盖而非新增）。ChromaDB 这类向量库就提供了 `collection.upsert`。Stripe 的公开 API 用专门的 `Idempotency-Key` 请求头做这件事，是支付场景下同一问题的教科书答案。反过来，没有幂等保护时，"读超时后重试写操作"就是在赌"上次一定没执行成功"——而我们已经看到，读超时恰恰意味着你不知道有没有执行。

最后是异常本身。`except Exception: return None` 有三宗罪：其一，`Exception` 几乎捕获一切——响应结构变了抛的 `KeyError`、参数写错抛的 `TypeError`，全被当成"网络不好"抹平，你丧失了发现代码 bug 的通道；其二，`None` 会作为合法数据继续向下游传播，真正的崩溃点远离真正的错误点；其三，traceback 丢失，事故无法复盘。正确姿势是：**捕获范围尽可能窄，处理不了的原始异常用 `raise NewError(...) from e` 包一层再抛**——Python 的异常对象自带 `__context__` / `__cause__` 链式记录（官方文档"Exception context"一节），`from` 就是在填写这条链，让三天后看日志的人知道"包装错误的原始错误是什么"。再给一个冷知识：Python 内置的 `TimeoutError` 属于 `OSError` 家族，而 `requests` 的超时异常在它自己的 `RequestException` 层级里——`except TimeoutError:` 抓不住 `requests` 的超时，这是真实存在过的线上事故来源。

## 把系统画出来

```
 客户端                                   服务端
   │
   │ ① 建立 TCP 连接          ────▶
   │    connect 阶段失败
   │    → ConnectTimeout / ConnectionError
   │    → 请求几乎肯定未送达 ⇒ 重试安全
   │
   │ ② 发送请求               ────▶   接收 · 执行 · 可能已写入
   │
   │ ③ 等待响应字节  ◀─ ─ 超时无新字节 ─ ─
   │    read 阶段超时
   │    → ReadTimeout
   │    → 对面状态未知：可能已完整执行！
   │    ⇒ 只有幂等操作才允许重试
   │
   │ ④ 收到完整响应（200 + body）        唯一"确知结果"的时刻
```

## 放回三个项目中看

### ML/DL 概念层

课程一的 Day 5 区分过 loss（训练时优化什么）和 metric（评估时衡量什么），今天这条链的镜像是：**错误是系统的信号，处理策略决定了信号有没有被丢弃**。静默吞掉的失败等于从数据集中悄悄删样本却不记录——几个月后你无法区分"这份知识不存在"和"那次 embedding 调用失败了"，检索评估的分子分母都被污染。这和误用 test 集调参一样，属于"没人的操作是错的，但结论已经不可信"的类别。

### Python / AI Backend 工程层

昨天说 contract 定义"正确的返回"长什么样，今天补上另一半：contract 还应声明**失败时抛什么**。一个标注 `-> list[SearchResult]` 的函数在出错时返回 `None`，等于类型撒谎——`Optional` 不在签名里，调用方凭什么防？重试逻辑还是 asyncio 场景的高危区：挂死的 HTTP 请求会占住事件循环，异步服务里超时必须用 `asyncio.timeout()` / `wait_for` 显式声明；而 `CancelledError` 继承自 `BaseException`、不被 `except Exception` 捕获是有意设计——取消不是错误，别拦截。测试上呼应 Extra Skill 暴露过的薄弱点：测重试必须断言"真的进入了异常分支"，比如 mock 传输层"先失败后成功"，再断言底层被调用了 2 次，而不是让测试在第一个提前返回处悄悄通过。

### Neural Garden 项目层

依据任务建立时提供的项目状态快照：当前 ingestion 链路里**没有**重试、没有 ingestion status 记录，也没有结构化错误留痕；同时快照明确记录了两条风险——文档更新可能"先删除旧数据再处理新数据"，失败时丢失上一可用版本；SQLite 与 ChromaDB 之间没有共享事务。用今天的框架看，"先删后写"让读超时重试变得比一般写更危险：删旧版成功后 embedding 调用超时，此时重试的前提是"写入新版"幂等，否则就是拿用户可见的检索空缺去赌运气。今天知识支持的决策是：① 重试策略必须建立在稳定 chunk id + upsert 之上，顺序应该反过来——先写新版、确认成功后再删旧版；② 是否值得做完整的 per-chunk 退避重试，取决于真实失败率证据：先带结构化日志跑 50–100 个批次，统计 embedding 与向量写入的失败率，若低于千分之一，"标记失败文档、整批重跑"就够，不必先建设复杂的重试队列。这些都是基于快照的分析，不是已完成的功能。

## 最容易踩的两个坑

**坑一：把所有超时当同一种错误，对非幂等写盲目重试。** 后果是把一次未知变成三次确定的重复：三份向量、三笔计费、或"删旧版后重写两次"引发的版本错乱。判断口诀——只有当"对面可能已执行"与"重复执行无害"同时成立，读超时后的重试才是负责任的。

**坑二：用 `except Exception: return None` 维持表面稳定。** 报错日志干干净净，缺向量的 chunk 却持续增长；更隐蔽的是它顺手吞掉编程错误，让本可以十分钟定位的 bug 变成三周后的悬案。失败要么按类型处理，要么带上下文向上抛；如果真要"降级返回空结果"，也必须让降级本身可见——记日志、加指标、在返回值里区分"没有结果"与"获取失败"。

## 面试官可能继续追问

> "你的 ingestion 管道调用 Embedding API，某次请求读超时了。这一刻你知道什么、不知道什么？你重试还是不重试？"

回答骨架：

1. **先给结论**：我知道对端已收到请求、不知道它是否执行完成；重试与否取决于写操作是否幂等，我的设计里每个 chunk 有确定性 id、写入是 upsert，所以重试安全。
2. **再解释原因**：读超时只表示"超时窗口内没收到响应字节"；无幂等保护时重试可能重复写入，有幂等保护时不重试反而永久丢一条数据——两害相权靠设计消除，而不是靠运气。
3. **落到场景**：在我的知识库里，向量写入以 `hash(doc_id+chunk_seq)` 为主键用 upsert，SQLite 侧记录每次 ingestion 尝试的状态，失败留痕、可重放；退避策略区分 429（尊重 Retry-After）与连接类错误；4xx 终止性错误直接报警，不进入重试。

## 合上文档前的 60 秒

**今天最重要的三句话：**

- connect 超时≈"没送到"，read 超时≈"不知道"——同一类异常，两种重试资格；
- 重试的安全性来自幂等设计，不来自把次数设成 3；
- 吞掉异常不会消灭失败，只会消灭失败的可见性。

**60 秒口头题：** 回忆你最近写的一次网络调用。它有没有设置 timeout？没设会发生什么？catch 的是哪个类、覆盖了哪些错误、吞掉了哪些错误？如果它现在要改成重试三次，最先需要补的保护是什么？
