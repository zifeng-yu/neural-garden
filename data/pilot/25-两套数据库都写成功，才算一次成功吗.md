# Day 10｜两套数据库都写成功，才算一次成功吗

> 日期：2026-09-17
> 预计阅读：约 20 分钟
> 今日只回答一个问题：当一次写入必须同时落在两个存储系统上时，失败会以什么形态出现，系统又该靠什么回到可信状态？

## 开场：事情从哪里开始失控

**假设场景：** Neural Garden 里一份 Markdown 文档被更新，标题改了，正文重写了。摄取管道照常运行：Header Split、分块、Knowledge Unit 提取、关系更新，全部写进 SQLite，日志显示"处理完成"。最后一步是更新 ChromaDB——先删除 12 个 Knowledge Unit 的旧向量，再插入新向量。删除完成了，插入执行到第 3 个，进程被杀。三天后用户抱怨："我改过的内容怎么搜不到了？"一查，SQLite 里是新数据，ChromaDB 里对应位置空了 9 个。没有报错，没有告警，系统"安静"地失忆了。

这就是今天要拆解的失败形态：双写部分失败。

## 先给结论

第一，跨两个存储系统的写操作，在单个程序里没有你可以依赖的原子性。SQLite 的事务只覆盖这一个数据库连接的读写；ChromaDB 活在另一个进程、另一套引擎里。越过这条边界，"要么都成功、要么都回滚"就是幻觉——"一半成功"这个中间态是客观存在的。

第二，问题的正确提法不是"怎么让两次写变成原子"，而是"怎么让中间态可检测、可表达、可修复"。标准解法组合是：指定一个权威事实来源（source of truth），给记录加 ingestion status 与 pipeline version，再用一个可反复运行的 reconciliation（对账）流程，把实际状态持续收敛到期望状态。

第三，重试不是补丁，是设计问题。重试的前提是幂等（idempotent）：同一次修复做一遍和做两遍结果相同。"先删后写"恰恰是破坏幂等的写法。

## 事情为什么会这样

顺着数据流展开。一次逻辑上的"更新文档"，物理上是一串分开写。沿用开场场景：文档切出 12 个 Knowledge Unit，管道动作依次是：

1. 新 chunks、Knowledge Units、关系写入 SQLite——成功；
2. ChromaDB 删除这 12 个单元的旧向量——成功；
3. 计算新 embedding 并插入——插到第 3 个，进程死亡。

此刻两边状态：SQLite 全新；ChromaDB 剩 3 个新向量、缺 9 个。没有任何一步报"整体失败"——第 1 步确实成功，第 2 步确实成功，第 3 步部分成功。这种没有全局回滚的失败，叫 **partial failure**（部分失败）。

下次查询时，向量检索只能在现存向量里找最近邻。缺掉的 9 个 Knowledge Unit 对检索器完全不可见——不是排名低，是不参与计算。这就是 **missing vector**（缺失向量）：召回率无声下降，没有异常抛出。对比另一种排法："先插新、再删旧"，如果死在删除前，向量不会缺失，而会变成 **stale vector**（过时向量）：还能搜到，命中的却是旧文本。missing 让系统"看不见"，stale 让系统"看见已经不为真的东西"——后者往往更危险，因为它会持续产出自信的旧答案。

为什么系统自己察觉不到？因为"成功"的定义是写入方自报的：SQLite 写完没抛异常就算成功。读取方、修复方、监控方都不知道"这 12 个单元应该各有一个新版本向量"这个期望是否被满足。

修复思路只能反过来构造：先让系统能表达期望，再拿现实去比对。落到工程上是三层：

- **ingestion status**：每个 Knowledge Unit 在 SQLite 里有状态字段，比如 `pending → stored → embedded → indexed`，只有向量库确认之后才能推进到最后一态。failed 或停在中间态的记录，天然构成一个可被发现的重试队列。
- **pipeline version**：把内容 hash、prompt 版本、embedding 模型、管道版本编进一个版本值，写进向量 id 或 metadata。这样对账时才分得清"向量缺了"和"向量在但属于旧版本"。
- **reconciliation（对账）**：一个可反复运行的过程——从 SQLite 读"应存在的向量集合"（期望），从 ChromaDB 读"实际存在的集合"（现实），求出差分，按差分做幂等补写或删除。

拿一个类比：家庭记账与银行转账。你的账本（SQLite）和银行账户（Chroma）是两套独立记账系统，一笔转账没法在一个事务里原子完成。银行的做法不是追求原子，而是先记"处理中"，再靠清算过程把两套账收敛。映射回来：SQLite 是账本、权威事实来源；ChromaDB 是派生索引，允许滞后、允许修复，极端情况允许从账本全量重建。关键判断是顺序——永远先确认权威侧，再动索引侧；反过来做，权威数据会被一个坏索引污染。

## 把系统画出来

```
                文档更新请求
                     │
        ① 写新版本, status = pending_embed
                     ▼
            ┌──────────────────┐
            │      SQLite      │  权威事实来源
            │ 12 个 KU + 状态  │  携带 version / status
            └────────┬─────────┘
                     │ ② embed + upsert（稳定 id，可重试）
                     ▼
            ┌──────────────────┐
            │     ChromaDB     │ ② 失败 → 两库分叉
            └────────┬─────────┘     （无报错，静默）
                     │ ③ 定期/事后比对
                     ▼
        ┌─────────────────────────────────┐
        │   reconciliation worker         │
        │ 期望(SQLite) ⊖ 实际(Chroma)     │
        │   = missing / stale / orphan    │
        └──────────────┬──────────────────┘
                       │ 重放幂等修复操作
                       ▼
                  最终收敛到一致
```

| 差异类型 | 怎么产生 | 对检索的影响 | 怎么发现 |
|---|---|---|---|
| missing vector | 旧向量已删、新向量没写全 | 该记录从召回中静默消失 | SQLite 期望集合中查不到对应 id |
| stale vector | SQLite 已更新、向量仍是旧版本 | 命中旧内容，自信地答错 | 比对 id 上的 version/hash |
| orphan（孤儿向量） | SQLite 已删除、Chroma 删除失败 | 已删内容仍被搜出 | Chroma 实际存在但期望中无 |

## 放回三个项目中看

### ML/DL 概念层

Day 5 讲 train/validation/test 与 data leakage，核心教训是：评估信号必须独立于被调优的操作，指标才可信。双写系统同理——"我写完了"不能作为"它可被检索"的证据，就像拿训练集 loss 声称泛化能力一样。"可被检索"的真值只能来自读取方视角：跑一次查询，该命中的记录在不在候选集里。回看 Day 1–2，建立评估 baseline 和建立对账，本质是同一件事：把"看起来能用"变成"期望集合与实际集合的比对"。

### Python / AI Backend 工程层

- 异常路径：昨天（Day 9）的 `except Exception: return None` 在今天这个场景里就是帮凶。向量写入步骤吞掉异常，状态机就不知道停在哪。正确做法：捕获具体异常，把记录 id、重试次数、失败原因落库，状态推进到 failed，让对账器能找到它。
- 重试分类：连接超时、429、5xx 是 retryable error，配 backoff；embedding 维度不匹配、输入为空是 terminal error，重试无意义，立刻终止并标记失败。
- 测试设计：Extra Skill 暴露过的弱点是"测试看似覆盖、实际没命中目标路径"。失败分支要靠故障注入来测：mock 一个在第 4 次 insert 抛异常的 Chroma client，断言状态停在 pending_embed、且 reconciliation 能修复——断言必须真正命中中间态，而不是只断言"最终成功"。
- 并发：两个 worker 同时跑对账，会重复算 embedding（双倍花钱）、互相覆盖写入。至少需要锁或分片归属。

```python
@dataclass
class VectorRef:
    vector_id: str   # hash(doc_id, chunk_idx, pipeline_version)
    version: str     # content_hash + model/prompt 版本

def reconcile(expected: dict[str, VectorRef],   # 来自 SQLite
              actual: dict[str, VectorRef]      # 来自 ChromaDB metadata
              ) -> dict[str, list[str]]:
    missing = [i for i in expected if i not in actual]
    orphan  = [i for i in actual if i not in expected]
    stale   = [i for i, r in expected.items()
               if i in actual and actual[i].version != r.version]
    return {"missing": missing, "stale": stale, "orphan": orphan}
# 修复：upsert(missing + stale)；delete(orphan)
# 全部按稳定 id 幂等，此过程可安全重放
```

### Neural Garden 项目层

根据任务建立时提供的项目状态快照：SQLite 结构化存储、ChromaDB 向量存储、Knowledge Unit 向量检索已经实现；而 ingestion status、pipeline version、失败恢复、SQLite–Chroma 对账，都不在已实现清单里，应视为"准备实现"。快照还明确记录了两条已知风险：文档更新可能先删除旧数据再处理新数据，失败时失去上一可用版本；两个存储之间没有共享事务。今天这篇对应的正是当时 ROI 路线的第 5、6 项。

动手之前需要什么证据？先做一次手动 diff：从 SQLite 导出"应存在的向量 id + 版本"，与 ChromaDB 的实际 metadata 比对，看现存量测差异有几条、各属哪类。如果差异为零且删除窗口很窄，这件事可以排在评估数据集之后；如果已有分叉，先做最便宜的两步——把向量 id 稳定化并改用 upsert 消除"先删后写"，再谈状态机和后台 worker。面试表述上，"快照中存在已知的双写缺口，我设计了收敛方案"是加分；把没实现的对账说成已实现，是一问就穿的硬伤。

## 最容易踩的两个坑

**坑一：去找"分布式事务"当救世主。** 看到双写，本能是加 2PC（两阶段提交）把两边绑成原子。但 Chroma 这类向量库不提供 prepare/commit 语义，自研事务协调器只会扩大失败面。工程答案是接受最终一致：单库事务保住权威侧，状态与版本表达中间态，对账收敛现实与期望。追求原子性的方案，隐含要求每个组件永远在线——那才是真正脆弱的系统。

**坑二：手动补一次数据，就当机制解决了。** 事故后人工把缺的向量补回去，问题"看起来"关闭了；可分叉在每次失败的更新里都会重新产生，一次性修复只覆盖过去。反过来说也不必一步到位建完整的后台控制器：v0 可以是一个手动触发、输出三类差异的 diff 脚本——可重复运行比优雅重要，频率可以之后再升级。

## 面试官可能继续追问

"你打算建评估集，用 qrels 比较 BM25 和向量检索。但如果向量库因为双写 bug 本身是不完整的，指标差的是算法还是数据完整性？这时评估结论还可信吗？"

回答骨架：
1. 先给结论：不可信。所以一致性校验必须放在评估之前，作为 eval runner 的前置断言（期望向量数 == 实际向量数）。
2. 再讲原因：如果 Vector 侧基线悄悄缺了 9 个向量，Recall@K 被系统性压低，可能直接得出"放弃向量检索"的错误决策——用坏数据杀掉好组件。
3. 落到场景：这正是 Neural Garden 路线里，版本化与 ingestion status 紧挨着评估数据集的原因。先让期望可表达（version），现实才可比对（diff），比较才是同规格的。

## 合上文档前的 60 秒

今天最重要的三句话：
1. 事务只覆盖单库；跨库之后，你手里的选项只剩状态、版本和对账。
2. missing vector 让系统看不见，stale vector 让系统看见已经不为真的东西；两者都静默，后者更危险。
3. 幂等是"敢重试、敢重跑对账"的前提——重做一遍和做一遍结果相同，修复才可以无脑循环。

一个 60 秒口头问题：你的项目里，哪一步的"成功"信号是写入方自报的，而不是从读取方视角确认的？
